# Vega chain map — sources, stages, artifacts, gates

This is the routing table `/vega` reads. One row per stage: what it consumes, what it produces, how the orchestrator checks the product, and whether the stage stops for a human. The orchestrator never restates a stage's procedure — it invokes the stage's skill and checks the artifact against this table.

## Source kinds

Vega classifies what it finds at the project root (or at the path given) into one or more **sources**. A project can have several; each opens its own lane, and lanes meet at the model.

| kind | recognised by | first stage |
|---|---|---|
| `codebase` | source files with an entry point (build manifest, `main`, server bootstrap) and no dataset | `spec-analysis` |
| `data-project` | notebooks, ETL / pipeline code, DAG definitions, SQL migrations alongside data files | `spec-analysis --kind data-project` (the code) and `dataset-forge` (each dataset) |
| `database` | DDL / schema files, ORM models, migrations, or a connection string the user gives | `spec-analysis --kind database` |
| `prose` | `.md` / `.txt` notes, an idea typed by the user, an existing `spec-analysis*.html` | `domain-forge` |
| `dataset` | `.csv .tsv .parquet .xlsx .json .jsonl` with tabular content | `dataset-forge` |
| `model` | an HTML with `<script id="domain-model" type="text/turtle">`; its `ex:sourceKind` and its layers (`strip_layer.py --list`) say where it is in a lane | the next stage its layers imply (below) |
| `blueprint` | a `blueprint-runs/<ts>/` directory with `blueprint.md` + `findings.json` | `document-project`; `/architect` is named as an option once code exists, never scheduled (below) |

## Stages

Two checks precede every row's *orchestrator's check* for the eight package stages (`forge-data`, `lens`, `shape`, `net`, `train`, `eval`, `pack`, `show`) and are not repeated in the table: **published** — the stage opened its layered HTML in the conversation before summarising (the summary's first line names it; missing → `FAIL: artifact not published`, the orchestrator opens the file and records the omission as a `WARN:`), and **briefed** — `docs/<stage>-brief.md` exists in the stage's run directory per `brief-contract.md`, its `records` present with matching digests (missing → `FAIL: no stage brief`, the stage is re-run naming the omission). `blueprint` writes its own `docs/blueprint-brief.md` in `blueprint-runs/<ts>/` (its patched SKILL.md) and is checked the same way; the external stages (`spec`, `forge-prose`, `refine`, `questions`, `chat`) are checked by their row only. `show` is the one **post-report** stage: it is briefed and checked like the others — its run directory is the showcase directory `<bundle dir>/showcase/`, its brief `<bundle dir>/showcase/docs/show-brief.md` with `post_report: true` — and its brief is never a chapter of `document`.

| document | `/document-project vega <lane> [<stage>]` (Vega mode — the patched skill; with `<stage>`, that stage's chapter only) | the lane's `docs/*-brief.md` in chain order, the layered HTML, the run directories | `docs/` LaTeX sources and the compiled PDF, one chapter per brief | PDF compiles; one chapter per brief in lane order (the post-report `show` brief excluded); the verifier reports every number resolved to a brief's `records` | the orientation plan, then chapter-by-chapter | not run (announced as pending — the loop needs its author) | chapter by chapter; a new brief (a re-run stage) → its chapter regenerated |
| show | `/vega-show <model.pack.html> [--report <docs dir>] [--plan <story-plan.json>] [--carry <story-plan.json>]` | model with `bundle` (the six layers `geometry`, `shape`, `architecture`, `training`, `evaluation`, `bundle`; `analysis` optional); the bundle with an online service and its showcase slot (`MANIFEST.serve.showcase_slot`); the compiled report, its `.aux` and `docs/label-roles.json` when `document` ran | `<stem>.show.html` with `showcase` layer; `<bundle dir>/showcase/` (`SHOWCASE.json` pinning every served file, the bundle `MANIFEST.json` digest and the report digests; `page/`, `page.json`, `story.json`, `plan/`, `data/attribution.json`, the report copy or the stage briefs); the previous showcase kept as `showcase.prev/`; memory § Network stances `show:` lines | `validate_model.py` exit 0 (13–16), `smoke_show.py <out> --strict`; `build_showcase.py --check <bundle dir>/showcase` exit 0 (`SHOWCASE.json` pins the current bundle `MANIFEST.json` and report; 2 broken, 3 stale); `smoke_show.py --serve <bundle dir> --strict` pass (`/v1/showcase` verified, every view walked, no unresolved placeholder, links at their pinned digests) or `WARN: served page not checked`; the bundle's `MANIFEST.json` digest unchanged | `FORK:` S1 no report (continue with brief links, or `document` first); S2 class roles, when an `alert` colour lacks a recorded basis; S3 motif, when the modality admits more than one | `--unattended`: runs; no report → brief links with `WARN:`; an `alert` role without a basis → `plain` with `WARN:`; the modality's base motif, marked | invoke again (rebuilt in place, previous kept as `showcase.prev/`); `--plan <edited story-plan.json>` for wording; `--carry <old plan>` on a new bundle; re-run whenever `--check` says stale |

Stems follow the chain's append rule (`domain-forge/references/future-skills.md` § naming): `orders.csv` → `orders.domain.html` → `orders.domain.analysis.html` → `orders.domain.analysis.shaped.html` → `….shaped.vega.html` → `….vega.train.html` → `….train.eval.html` → `….eval.pack.html` → `….pack.show.html`; a user-chosen `--out` is recorded in the ledger and routing reads the file's layers, never its name.

The four `net` … `pack` stages are the **network sub-chain** (skills `vega-forge`, `vega-train`, `vega-eval`, `vega-pack`; `vega-forge` owns their platform). Two facts about them the orchestrator must carry: **the test part is sealed** from `net` through `train` and opened once at `eval` — a lane whose `test_seal.json` exists is recorded with its exposure count, and a new `train` after `eval` is invoked with `--after-eval` and noted in History; and **a campaign may run elsewhere** — `train --emit-only` ends in a `GATE:` that hands the user a directory to execute on another machine, and the lane waits at `train` until `--import-run` brings it back (the ledger's **Open** holds the hand-over). `show` (skill `vega-show`) is the presentation stage after the sub-chain: it reads the bundle and never writes a file the bundle's `MANIFEST.json` pins; its product is served by the bundle's own service through the showcase slot.

`architect`, `improve` and the sketched chain skills (`instance-create`, `code-implement`, `countergen`, `model-diff`) are **not** stages Vega schedules: they are named in the summary as options when their input exists and the skill is installed, never invoked on its own initiative.

## Destinations — what the user may be after

Step 4 of the procedure reads this table and keeps the rows this project's state and environment allow. A destination is a place to stop, not a stage: it names the goal stage, the lane that reaches it, and — the column that keeps the choice honest — what it does **not** give you.

| the user wants | goal stage | runs | does not give you |
|---|---|---|---|
| to know where the project stands | none (`status`) | nothing | any new artifact |
| to understand a dataset before deciding anything | `lens` | `forge-data` → `lens` | transformed data, an architecture |
| a cleaned / training-ready dataset | `shape` | … → `lens` → `shape` | a trained model, a pipeline to run it in |
| the data / ML pipeline architecture | `blueprint --mode pipeline` | … → `shape` → `blueprint` | code, a deployment, a trained model |
| a trained and evaluated network | `eval` | … → `shape` → `blueprint` → `net` → `train` → `eval` | a deployable artifact; the test part is opened once on the way |
| a deployable predictor (bundle, model card, optional service) | `pack` | … → `eval` → `pack` | integration into your system; a verdict better than the evaluation's |
| a demonstration page others can open (the network explained, one row followed through it, the results, the code with report notes) | `show` | … → `pack` → [`document` →] `show` | a new measurement or a better model; a page for a bundle without an online service (batch and stream bundles need `pack --serve`); anything the report does not already say |
| to understand an existing codebase | `spec` | `spec` | a formal model, a refactor |
| a queryable domain model | `forge-prose` | `spec` → `forge-prose` | an architecture |
| an answer to one specific question, now | none — `/model-chat` or the `lens` dialogue | one loop, no lane advance | any lane progress (nothing is recorded as a stage) |
| the open questions a model leaves | `questions` | `questions` on the current model | answers |
| book-quality documentation | `document` | everything above, then `document` | anything the earlier stages did not settle |

**The documentation modifier.** Any destination may carry `+document`: the lane runs to its goal stage and then proposes `document` — the step-by-step PDF built from the stage briefs the lane left (`brief-contract.md`). It is offered in the same question as the destination, never in a second one, and only when the environment has LaTeX and `document-project`. Without it the user still has every stage's interactive HTML and brief, and `/document-project vega <lane>` remains an option the summary names.

Two rows are deliberately outside the lane order: a *question now* is answered by a loop skill and advances nothing, and *status* produces no artifact at all. Offering them keeps the menu honest — a user who only wanted to look should not be routed into a forge.

## Lanes — the default order per source

```
codebase ──► spec ──► forge-prose ──► [questions | chat] ──► blueprint(system) ──► document
prose ────────────► forge-prose ──► [questions | chat] ──► blueprint(system) ──► document
database ─► spec(database) ──► forge-prose ──► … (same as codebase)
dataset ──► forge-data ──► lens ──► shape ──► blueprint(pipeline) ──► net ──► train ──► eval ──► pack ──► document ──► show
data-project ─► spec(data-project) ──────────────────────────┐
               dataset ► forge-data ──► lens ──► shape ──────┴─► blueprint(pipeline: both inputs) ──► net ──► … ──► document ──► show
model ────► (read its layers) ──► the first stage of its lane whose product is missing
```

`blueprint(pipeline)` is **required** before `net`: the network sub-chain builds the network inside the blueprint's world model (its ports, module map and value objects, in machine form in `pipeline.json`), so a lane whose objective is the network runs the blueprint on the way — `--report-only` unattended, gated attended — and Vega never proposes `net` without a matching `pipeline.json`.

`show` follows `pack` directly when the lane does not document (or unattended, where `document` is pending), and is re-run once the report exists: the showcase pins the report, never the other way round, so a new report digest makes it stale.

`questions` and `chat` are optional stages on every lane: Vega proposes `questions` after a forge when the model has rule layers or a rationale with named external systems, and never schedules `chat` on its own — it names it.

## Reading a model's position from its layers

| Turtle / layers found | lane | next stage |
|---|---|---|
| `ex:sourceKind "dataset"`, no layers | dataset (a stripped or standalone model) | `forge-data` refine (`/dataset-forge <model>`) to regenerate `geometry`; `lens --standalone` only if the user says geometry is not wanted (Vega proposes the refine) |
| `geometry` | dataset | `lens` |
| `geometry` + `analysis` | dataset | `shape` |
| `geometry` + `analysis` + `shape`, no matching `pipeline.json` | dataset | `blueprint --mode pipeline` (required before `net`; the row below applies once it exists) |
| `geometry` + `shape` (no `analysis`), no matching `pipeline.json` | dataset | `blueprint --mode pipeline` (Vega notes that `lens` was skipped) |
| `geometry` + `shape` (+ `analysis`) and a `blueprint-runs/<ts>/pipeline.json` whose `input.model_digest` equals the model's canonical Turtle digest and whose `input.shape_manifest_digest` equals the shape layer's manifest digest | dataset | `net` (`/vega-forge <model> --pipeline <pipeline.json>`); without a matching `pipeline.json` the next stage is `blueprint --mode pipeline`, whatever the objective |
| `architecture` | dataset | `train` (`/vega-train <model>`; if the run directory holds `ladder.json` and `runs/` but no `training` layer, the campaign was run elsewhere or interrupted: `--import-run` or `--resume`) |
| `architecture` + `training` | dataset | `eval` (with the attended gate); if `test_seal.json` exists in the campaign, the lane's evaluation exists elsewhere — find its file or re-run with `--again` |
| `architecture` + `training` + `evaluation` | dataset | `pack`, unless the evaluation's verdict is *not earned* — then, attended, Vega proposes `pack --ship-anyway` **and** `train --after-eval` as alternatives, naming the verdict, and asks; unattended, nobody is asked and the `pack` row's unattended behaviour applies (no `--ship-anyway`: `WARN:` and stop) |
| `… + bundle` | dataset | `document` when the objective carries `+document` and no report exists (unattended, where `document` is pending, `show` runs now with brief links when the objective includes it); else `show` when the objective includes it; else the lane's end (the bundle directory named in the summary) |
| `… + bundle + showcase` | dataset | `show` again when `build_showcase.py --check` exits 3 (the report's or the bundle's digest moved, a re-emitted bundle, or a report now exists where the layer records brief links); else the lane's end (the serve command named in the summary) |
| software model, no layers | software | `questions` (proposed) or `blueprint --mode system` |
| any model + `open-questions` with open rows | any | `refine` (the questions are the refine's brief) or `chat` |
| any model + `chat` | any | whatever the lane says next; the chat is context, not a stage |

A refine's output supersedes its predecessor for routing — recognised by the ledger's History (Vega recorded the refine) or, for a file produced before the ledger existed, by the user's word and the memory stances; the predecessor stays in the ledger as history.

## Stage prerequisites Vega checks before invoking

`python3 vega/scripts/env_check.py --env` answers all of this in one line and one exit code; the list below is what it checks and why.

- Every stage: the consuming skill is installed (its `SKILL.md` is listed by the runtime) **and its scripts exist** — `env_check.py --env` checks exactly this, because a skill whose `SKILL.md` names a script the directory lacks is a specified-but-unbuilt stage: `ERROR:` naming the script, lane closed there. `domain-forge` is installed for any stage that reads or writes a model; `effective-java` (an external skill, not part of this package) for `blueprint`.
- `forge-data`, `lens`, `shape`: Python 3 with `pandas`, `numpy`; `scipy`/`scikit-learn` for `lens` and `shape`; `geopandas` + `pyproj` only when `context.spatial` is non-empty; a headless Chromium for symbolic verification and smoke tests (without one the stages degrade as their own SKILL.md says — Vega records `WARN: no headless browser` once in the ledger, not once per stage; a `smoke_*.py --strict` run fails only on **page** errors — a browser-internal stderr line such as a GCM or GPU notice is not a defect of the layer and is never a `FAIL`).
- `blueprint`: the `effective-java` skill for the anchor corpus.
- `net`, `train`, `eval`, `pack`: `vega-forge` installed with its scripts (it is the platform of the other three, as `domain-forge` is of the chain); the `architect` skill with `--baseline`, the `improve` skill and the `effective-java` corpus for the conformance gate (mechanical checks C0–C14, then `/architect --baseline`, then `/improve --report-only`, each judgement tool's structural or divergence findings confirmed when two of three independent audits reproduce them, and advisory — unattended a `WARN:` and an open item, attended a `FORK:` — `code-contract.md` §5; without `architect` or `improve` the gate is mechanical only and every `net` and `pack` layer says so — `WARN:` recorded once); a `blueprint(pipeline)` run for `net`; the backend named in the spec (`torch` ≥ 2.2 for `pytorch`) importable; `jupyter` + `nbconvert` for executed notebooks (without them the stages emit unexecuted notebooks and say so — a `WARN:` recorded once); `optuna` optional for `train` (random search otherwise, said so); `lightgbm` optional for `eval` (scikit-learn's HGB otherwise); a GPU optional (`--device`); `dataset-shaper` whose `shape.py` accepts `--transform-only` for `pack` (`env_check.py` reads the flag from the script); `fastapi` only with `pack --serve`; `onnx` only with `pack --export onnx`. `env_check.py --env` reports the backend, Jupyter, Optuna and the GPU on the same line as the rest.
- `document`: a LaTeX toolchain and the `document-project` skill with its Vega mode (`env_check.py` reads `vega` from its SKILL.md); the lane's briefs, which the package stages write on every run.
- `show`: `vega-show` installed with its scripts and its page template (`assets/page/` with `TEMPLATE.json`); the bundle packed by a `vega-pack` whose serving templates carry the showcase slot (`serve/routes_showcase.py`, written into the bundle as `MANIFEST.serve.showcase_slot` — `env_check.py` reads both and reports `vega-show` unbuilt without them) with an online service (`pack --serve`); `torch` for the preflight's `predict.py --check`; `fastapi`, `uvicorn` and a headless Chromium for the served check (without them the served page is not checked — `WARN:` recorded once); LaTeX is **not** needed (the stage reads the compiled report). A `document-project` without the label-role map is reported `DEGRADED`: `show` still runs, linking the stage briefs or proposing report roles from the `.aux`.

A missing prerequisite is an `ERROR:` for that stage and a `WARN:` for the plan; Vega proposes the stages that can still run.
