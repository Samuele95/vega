# Vega notebook contract — the notebook is the run, executed

Every Vega stage ships one Jupyter notebook beside its HTML layer: `engineer.ipynb` (`/vega-forge`), `train.ipynb` (`/vega-train`), `evaluate.ipynb` (`/vega-eval`), `predict.ipynb` (`/vega-pack`). The notebook is **not a report written after the fact**: it is generated from the same spec and run records the scripts used, it imports the same emitted code from its own directory, it is executed in place, and its outputs must equal the layer's numbers. A notebook that disagrees with its layer is a defect in one of the two, and the assertion cell at its end is what finds it.

## 1. Generation — `vega-forge/scripts/nb_emit.py`

`python3 <vega-forge>/scripts/nb_emit.py --stage forge|train|eval|pack --from <dir> --out <dir>/<name>.ipynb` builds the notebook from the stage's records (`netspec.json` and `smoke.json`; the campaign's `experiments.json`, `ladder.json`, the runs' `history.jsonl`; `eval/<run>/metrics.json`; `bundle/MANIFEST.json`) and from the readings the skill authored for the layer (the same `readings.*` text, verbatim — the notebook and the layer never say different things). Only this script writes notebooks; no stage hand-writes cells.

**The cells drive the emitted adapter classes** (`backend-contract.md` §1): the DataSource is a `ShapedParts()` instance, the Trainer a `Trainer(store)` given the ModelStore, a `ModelRegistry()` (`fit(model, spec, data, callbacks, run=RunContext(...))`; the device, the loss and the learning-rate curve from the Trainer module's support files — `optim.device_for`, `losses.build_loss`, `optim.resolved_lrs` — the functions the Trainer itself calls, never a second door on the port), the Model is built by `Network.build(spec)` — each resolved by role through `blueprint-map.json`. `nb_emit.py` refuses (exit 2, before a cell is written) what its cells could not run: a package whose map does not record `generation: v2.3` (its adapters would be module-level functions); an evaluation whose `metrics.json` does not name `vega/predictions-layout@1`; a bundle whose `predict.py` exports no `check_examples`; a window bundle whose `MANIFEST.sample` carries no `history_rows`. A refused notebook is not written and the stage reports the refusal; it never hand-writes a substitute.

Every notebook has the same skeleton:

1. **Provenance header** (markdown): the stage, the chain input's path and canonical digest, the run directory, the spec digest, the backend and its version, the seed, the timestamp; and the sentence *"Generated by `nb_emit.py`; edit the spec or the run, not this notebook."*
2. **Environment cell**: `chdir`s to the **project root** (the spec's paths — `shaped/…`, `analysis/…` — are project-relative, and a replay that cannot open the parts is not a replay), pins `sys.path` to the notebook's own directory and imports what the stage needs from the emitted package **by role through `blueprint-map.json`** — the `Model`, `ModelStore`, `DataSource` and `Trainer` adapters live wherever the blueprint's module map put them (`registry/store.py` is as legitimate as `model/store.py`), so `nb_emit.py` resolves each import from the map and never assumes the emitter's default layout; for `engineer.ipynb` that is the network, the metrics, the data adapter and the loop; the same for `train.ipynb`, where the replay cell pins `runs/<selected>/` first when that run re-emitted its package (so the replay loads the code the run trained, not the root's); `<package>.model.metrics` and the stored records for `evaluate.ipynb` (never the network or the data adapter: the evaluation notebook loads no network); `from predict import load` only for `predict.ipynb` — the bundle's own composition root, and only in its verifying half; its explanatory half imports nothing but `json`, `pathlib` and `pandas`, because a notebook that could not render the card's numbers without torch installed would be a worse auditing tool than the card — prints versions and the device; fails loudly if a module is missing.
3. **One section per procedure step of the stage**, in the stage's order, each a markdown cell with the reading for that step followed by the code cells that reproduce the step's numbers from the records on disk (a section never recomputes what a script already computed unless recomputation *is* the check — see §2 per stage).
4. **Assertion cell** (`assert_matches`): loads the layer's data script from the stage's output HTML (or the record the layer was built from) and asserts, key by key with the stage's tolerance, that the numbers the notebook printed equal the numbers the layer carries. A failing assertion fails execution.

## 2. What each stage's notebook contains

**`engineer.ipynb`** — the decisions table rendered from `netspec.json` (choice, source, rationale); `build_model(spec)` and the parameter count per block; one forward pass on a real batch with the per-block output shapes; the loss written out and evaluated on that batch; **one manual optimisation step**: the gradient of the loss with respect to the head's weights computed explicitly, the optimizer's update rule applied by hand to those weights, compared to what one step of the backend's optimizer does (the didactic cell — it is what "documenting the weight update" means concretely); the schedule's learning-rate curve; the mechanics reading. The parameter count must be exact and the forward outputs within `1e-5`.

**`train.ipynb`** — the campaign: the ladder as a table (run, hypothesis, delta, source); per run, the history loaded from `history.jsonl` and drawn (loss and primary metric on train and valid, learning rate, global and per-block gradient norm, update ratio) with the run's reading; the diagnostics the catalog fired; the HPO study's trials and the importance of each searched dimension; the selection with its rule; **a re-execution of the selected run for `--replay-epochs` epochs (default 3)** that asserts the first epochs' records match `history.jsonl` within the backend's determinism tolerance (the replay keeps the spec exactly as that run resolved it — `runs/<id>/netspec.resolved.json` — and a callback stops it after `--replay-epochs` records) — the notebook proves the run is reproducible without paying for the whole run again; the campaign reading. The notebook emitted with `--emit-only` (remote execution) is a different file, `train.remote.ipynb`: it contains the **full** training of every ladder run as executable cells, so running it elsewhere produces the campaign; `--import-run` reads what it wrote, and the ordinary `train.ipynb` is then emitted from the imported records as above.

**`evaluate.ipynb`** — the seal (which run, when the test was opened, how many exposures); the metrics recomputed from `predictions.test.parquet` (the stored scores and labels — the network is *not* run again on the test part, so re-executing the notebook never re-exposes it) with the bootstrap CIs at the recorded seed; the curves; the slices; the baselines' metrics from their stored predictions; the verdict reading. Tolerance `1e-9` on point metrics, `1e-6` on bootstrap bounds.

**`predict.ipynb`** — the model card in code, and in the card's own order: §1 Identity (the chain's digests, and which `--include` shape this bundle is), §2 Task and data (the recipe's steps, the input schema, the analysis findings), §3 Architecture (the decisions with their sources, the loss and the update rule), §4 Training (the ladder, the selected run's curves with the checkpoint epoch marked, the diagnostics), §5 Evaluation (the seal and its exposures, the metrics with their intervals, the baselines and paired differences, the curves, the slices, the verdict), §6 Intended use verbatim, §7 How to use — and this is where it stops reading and starts running: load the bundle, call the bundle's own `predict.check_examples(<bundle>)` — `examples/rows.csv` through `predict`, compared with `examples/expected.parquet` at each `__row__` over the output record's compared fields at the round-trip tolerance and exactly over its decided fields (`bundle-contract.md` §5) — and assert it passed; a window bundle's single-row answer is asked with the `MANIFEST.sample.history_rows` rows before it as history; re-hash every file the manifest records, and print the usage lines (the extra `train.py` and `evaluate.py` lines for a `full` bundle, the REST scaffold and the exports when present). The explanatory half reads `records/<layer>.json` — the six layers copied into the bundle — and imports nothing, so it renders from a bundle whose code is broken; the verifying half imports `predict.py` and would not. §8 asserts both halves agree with the manifest: the run the seal recorded, the verdict, the primary metric.

## 3. Execution and verification

Notebooks are executed in place with `jupyter nbconvert --to notebook --execute --inplace --ExecutePreprocessor.timeout=<stage timeout> <nb>`; the stage's apply script, given `--notebook <path>`, writes the layer's `notebook` record itself (`executed` is true when every code cell carries outputs and none is an error output; `digest` is the file's sha256) — no stage types that record. Without Jupyter on the machine the notebook is emitted unexecuted, the apply script records `executed: false`, the stage adds `WARN: notebook not executed` to the layer's `markers`, and the summary says so — an unexecuted notebook is a `WARN:`, never silently a report. **A failing assertion is not the same thing:** it leaves an error output, the apply script records `executed: false` and prints `WARN: notebook not executed — a cell ended in an error output`, and that marker is a defect, not a degradation — the notebook and the layer disagree, so one of them is wrong; the stage finds which (the layer's numbers come from the records, the notebook recomputes them), fixes it at its source (the spec, the run, the records, `nb_emit.py`), re-emits and re-executes, and does not publish the layer while an assertion fails. Only the absence of Jupyter may ship an unexecuted notebook. The build's acceptance test (the Vega package's `tests/acceptance.py`) executes all four notebooks of the orders chain and requires every assertion cell to pass.

**Order within a stage.** The readings a notebook carries are the layer's readings, so every stage authors its layer JSON (the judgement) *before* emitting the notebook, emits and executes the notebook, and only then runs the apply script, which records the notebook's digest in the layer — judgement → notebook → apply, in every Vega SKILL.md.

**Multiclass records** are read as a matrix, never as one column: `evaluate.ipynb` rebuilds the prediction from `score_0 … score_{K-1}` (and each baseline's `score_<baseline>_<k>`), `predict.ipynb` compares every expected head column plus the decoded label — a single `score` column is the class-0 logit and "disagrees" with the evaluator by construction. Notebooks read only their own directory and the shaped data the spec names; they write only into their own directory (figures, the replay's scratch); they never reach the network. A cell that needs a GPU checks for one and falls back to CPU with a printed note; a stage timeout is a `WARN:` with the cell named.
