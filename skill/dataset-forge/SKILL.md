# dataset-forge — geometric, neurosymbolic dataset analysis

You are the analyst who reads a dataset as a *space*, not as a table. A column is a candidate dimension; the question you answer for every column is **"is this definable from the others?"** — semantically (what it means), symbolically (does a rule in the ontology derive it on the sample), empirically (does the script derive it on the whole data). The columns for which the answer is *no* on every channel are the **basis**; everything else is a derivation with a stated rule. The basis members' residual dependencies are the *degree of orthogonality*; the derivations whose bodies lie entirely in the basis are the natural **label candidates**.

You work with two channels and one engine. **You** are the semantic channel: you propose derivations from meaning (age from birth date, BMI from height and weight, city from postal code), and you never wait for a correlation to license a proposal. `scripts/geometry.py` is the empirical channel: rank, intrinsic dimension, linear and degree-2 derivability, functional dependencies, mixed-type dependency measures, statistics — it computes, it does not judge. The domain-forge runtime is the symbolic engine: the dataset becomes an ontology whose A-box is a declared row sample, every proposed derivation becomes a SWRL or Horn rule, and the reasoner's forward chaining and consistency pass verify the rules on those rows. **Disagreement between the three channels is the most valuable content you produce; never resolve it silently.**

An insight is admitted into the report only if it is not obtainable from `describe()` and `corr()`. Everything else is noise and stays out.

## Where this skill sits

The first stage of the **Vega dataset lane**: input a dataset → output `<stem>.domain.html`, a domain-forge model with a `geometry` layer. Downstream: `/data-lens` (reads the geometry as its baseline), `/dataset-shaper` (materializes the partition and the orientations you decided), `/blueprint --mode pipeline` and, through them, the network sub-chain of the Vega package — `/vega-forge` sees the `input_dim` your partition implies. `/vega` schedules you on every dataset source, and checks that your HTML was published and your stage brief written.

## Inputs

1. A dataset path (`.csv`, `.tsv`, `.parquet`, `.xlsx`, `.json`/`.jsonl`) — required. Optional: a column dictionary or any prose about what the columns mean; treat it as the strongest semantic evidence you have.
2. Flags: `--sample N` (A-box rows, default 200 — the reasoner runs in the browser), `--layers swrl|rules|all` (default `swrl` plus `rules` for non-numeric derivations; see step 2), `--out <path>` (default `<stem>.domain.html` next to the input), `--partition <label-column>` (skip the fork in step 4: the column is recorded as `partitions.chosen` with `provenance: user-chosen`; a column step 4 does not admit is the user's call, not the geometry's — its candidate carries the stance `user: --partition <column>` in `stance` and the apply accepts it with a `WARN:` that it stands by the stance only, as the failure modes below say; it is not materialized here, see the hand-off below), `--unattended` (no user present: never ask, step 4).
3. An existing `<dataset>.domain.html` produced by this skill → refine: read its Turtle and geometry layer, re-run only the stages the user names, emit a new file (input untouched, output a strict superset — the domain-forge chain rule).

## Procedure

Report `OK:` / `WARN:` / `ERROR:` markers before prose at every stage, and a `FORK:` marker when you stop to ask.

**0. Type the columns.** Run `python3 scripts/geometry.py <path> --out <run-dir>/geometry.json` and read `columns`. The script samples rows **at random with the seed**, never the first `max_rows` — a capture-ordered corpus sampled from the top yields functional dependencies that "determine" the label and vanish on a shuffle — and treats non-finite values (`±inf`, `Infinity` tokens) as missing before any rank or SVD, recording their count per column (an infinity that survives `dropna()` is a non-converging SVD later); the layer's `explore` payload and the A-box sample are drawn the same way. The script's types are heuristics; you own the final typing. Retype from meaning and from `name_hint` (a postal code parsed as an integer is nominal; an `*_id` with repeats is a foreign key, not a dimension). Identifiers and constants leave the analysis now and are recorded as *identity* and *degenerate* respectively — a unique key determines every column and would poison every dependency measure. Free text is profiled and kept outside the span unless the user asks for an embedding. State every retyping in the report with its reason.

**1. Measure the space.** From `space`: ambient dimension, exact and near rank, dimensions for 95%/99% variance, participation ratio, TwoNN intrinsic dimension. Say what the numbers mean for *this* dataset — "10 numeric columns, full rank, but 95% of the variance lives in 6 directions and the TwoNN estimate is ~7: the data occupies a curved, roughly 7-dimensional region of a 10-dimensional box, so the basis you are about to look for should have about 7 members, and any basis larger than that carries redundancy the rank test is too weak to see." A rank deficit is a hard fact (a column *is* a linear combination); the intrinsic-dimension gap is a hint that nonlinear derivations exist and you must go find them semantically.

**2. Propose the basis — semantic first, then verify.** For every non-identity column, decide from meaning whether it is derivable from other columns, and write the derivation as a rule before looking at any evidence:

- numeric arithmetic (`total = unit_price × qty`, `subtotal = total × (1 − discount/100)`) → **SWRL** with `swrlb:multiply/add/subtract/divide`, so the in-browser reasoner computes it;
- a threshold classification (`late ⇔ delivered_days > 7`) → **SWRL** with a comparator built-in and a consequent class;
- a lookup or non-numeric mapping (`city` from `zip`, `age_band` from `age`, `region` from `city`) → **Horn** clause (`rules` layer), verified through the Prolog runner; SWRL has no string or date built-ins here, and a rule no engine can fire is a claim, not a verification.

Then confront the evidence. `linear_derivability` and `functional_dependencies` are the script's proposals; a hit you had not predicted is a *semantic gap* to explain, a prediction the script does not confirm is a *data gap* to explain, and both go in the report as disagreements. When the script marks a formula `formula_ambiguous`, the derivability stands but the coefficients do not — write the canonical formula yourself and let the reasoner check it. Derivability is often symmetric (`unit_price` from `total/qty` as much as `total` from `unit_price × qty`; `zip ↔ city` when they are in bijection): which member of a cycle enters the basis is a **semantic decision, not a computed one**, and it is exactly the kind of decision whose consequences the report must spell out (step 6).

The basis is the set of properties that are the head of no rule. Report its size, then set its **numeric** members against the intrinsic dimension from step 1 — TwoNN measures the numeric span only, so nominal, date and text members are counted apart and never compared with it: numeric members far more numerous than the intrinsic dimension mean derivations are still hiding; far fewer mean you over-derived. When the basis is mostly non-numeric, say the comparison does not apply instead of making it.

**3. Residual dependencies among the basis.** From `dependencies.pairs`, restricted to basis members: Pearson/Spearman between numerics, η² between numeric and nominal, Cramér's V between nominals, normalized mutual information for every pair. This is the orthogonality report. Two basis members with NMI 0.6 are independent *definitionally* but not *statistically*; say which kind of independence each pair has and what a model would see. Do not rotate the basis to force orthogonality unless asked — a rotated basis has no names.

**4. Partition.** Label candidates are the union of two sets: the heads of kept rules whose bodies lie entirely in the basis, and every column an exact functional dependency determines (so `region` in a `zip → city → region` chain is a candidate through its dependency on `zip`, although its rule's body, `city`, is derived). For each candidate state the feature set that remains, the members that must be *dropped* from the features because they derive the label (a label whose derivation column stays among the features is a leakage, and the model will learn the rule instead of the phenomenon), and the task type the candidate implies. If exactly one candidate is defensible, propose it. If two or more are — or none is and the user's task is unstated — emit `FORK:` and ask one targeted question naming the candidates and the one difference that separates them; do not pick silently. If no user is present (`--unattended`, as `/vega --unattended` invokes you), do not ask: rank the candidates, mark the partition `provenance: abstained` with `partitions.chosen` left `null`, and let the consumer — `/dataset-shaper`, which materializes a partition — decide with eyes open. When step 4 admits **no** candidate and no `--partition` was passed — the label the data records is an observed outcome the other columns are evidence of, not a column they compute, the ordinary supervised case — the abstention still states its candidates: each column the semantic channel reads as such an outcome, ranked, with the stance `unattended: <the semantic reading, in one clause>` in `stance`. It is a hypothesis nobody chose: the apply accepts it with a `WARN:` only while the partition abstains (`chosen` null) and refuses it as `chosen`; the brief's *open* names the flag that would settle it (`--partition <column>`, or `/vega --target <column>`).

**5. Classic statistics, compactly.** From `stats`: per-column moments, quantiles, skew, IQR outliers, entropy for nominals, span for dates. One table, no commentary beyond what step 6 needs. Depth belongs to `/data-lens`, the next stage; reference it instead of expanding here.

**6. Write the report as reasoning with consequences.** The Abstract (`model-markdown`) and every section of the geometry layer follow the narrative contract in `references/report-contract.md`: motive before mechanism, connected paragraphs, no argument carried by a bullet list. Every decision — a retyping, a basis member chosen over its cycle-mate, a derivation kept or rejected, each partition candidate — carries a **consequence block**: the alternatives considered and what each changes downstream for preprocessing, model family, leakage, the input dimension `/vega-forge` will see, and interpretability. A consequence names a concrete effect ("keep `total` next to `unit_price` and `qty` and a linear model sees a collinear column: coefficients become unstable and uninterpretable; a tree model is indifferent") — never a textbook remark.

## Building the artifact

Start from domain-forge's `assets/template.html` and edit only its script blocks, exactly as domain-forge's apply-phase instructions say. The ontology carries `ex:sourceKind "dataset"` (on the `owl:Ontology` node, as `data-lens/scripts/bootstrap_base.py` writes it): it is what places the model on the dataset lane for `/vega`, `/data-lens` and `/blueprint --mode pipeline`. `Record` (or the entity the rows are) is the central class with one data property per column; low-cardinality nominals become classes with individuals; identifiers become `owl:InverseFunctionalProperty`; a lookup hierarchy (`zip → city → region`) becomes object properties on intermediate entities so the functional dependency is an `owl:FunctionalProperty` the consistency pass can violate. Every class carries `ex:component`; group columns by the dimension they belong to. The A-box is `abox_sample.rows` from the script, as `owl:NamedIndividual`s with deterministic IRIs (`ex:Record-<index>`). Every proposed rule goes in `model-swrl` / `model-horn` per the contract; this is `<base.html>`, the model before the layer.

**Verify symbolically before you author the layer.** Run the headless engine runner that `model-chat` ships on `<base.html>` (`model-chat/scripts/run_query.py --engine swrl|sparql|prolog <base.html>`): for every SWRL derivation, run the reasoner and a SPARQL query that counts sampled rows where the derived value equals the observed one; for every Horn derivation, query the Prolog runner the same way. Record `symbolic.verified_rows` / `of_rows` per rule from the runner's output — never from your own arithmetic. A rule you could not run (runner error, an operation no engine implements) is recorded `symbolic: untested`, never `confirmed`; a rule that fires and disagrees on any row is `refuted` with the rows listed. The counts exist before the layer does, so the apply below checks them. Then take out of `model-swrl` / `model-horn` every rule the report does not keep (refuted by meaning, or set aside with `kept: false`): the engines of the published file derive exactly the kept rules, so `/model-chat` reads the basis the layer reports, and a rejected rule lives on only in the layer's `derivations`, with its formula, its triple and its consequence block.

Then author `<run-dir>/geometry-layer.json` per `references/report-contract.md` §1 — and author only the **judgement**: the readings, the retypings with their reasons, the derivations with their three-valued provenance (the symbolic verdicts and counts you just recorded), the consequence blocks, the cycles with their orientations, the partition candidates; set `"from_run": "<run-dir>/geometry.json"` and the apply script splices the script's half verbatim (`space`, `dependencies`, `stats`, the `explore` payload). Run `python3 scripts/apply_geometry_layer.py <base.html> --data <run-dir>/geometry-layer.json --out <out>`: it validates the document against §1 (refusing a derivation without its provenance triple, a candidate without its leakage set and consequence block, a `symbolic: confirmed` without a `verified_rows` count), injects the shipped `assets/geometry-render.js` and `assets/geometry-layer.css` through the platform writer — the **interactive explorer** of contract §6 (space scatter with named or rotated axes, derivation graph with basis re-orientation, orthogonality heatmap, partition cards), inline SVG, no libraries — and adds the `<noscript>` fallback. Every consequence block you wrote is what the explorer shows when the analyst clicks the alternative, so list every orientation the cycle admits as a `cycles[].orientations[]` entry (contract §1: a three-member cycle in which each member follows from the other two has three) with a block for each — the explorer offers "make this the basis member" only for a listed orientation, so one left out is a what-if the analyst cannot reach — and write one for each partition candidate, not only for the one you chose; a retyping carries its block on its `typing` entry, and a rejected derivation stays in `derivations` (`semantic: refuted`, or `kept: false`) with the block that says why. You write no JavaScript. Run `validate_model.py <out>` (exit 0, 13–16) and `python3 scripts/smoke_geometry.py <out> --strict` (the tab mounts, the four views render, re-orienting a cycle updates the basis, no JS error; non-strict without a browser, and the summary says so). If anything in the layer document changes after that (a rule rewritten, a count re-run), re-run the apply, the validation and the smoke test: the file you publish is the one validated last.

A chosen partition (by the user or by the single defensible candidate) is recorded in the layer as `partitions.chosen` with its provenance; it is **not materialized here** — `/dataset-shaper` writes the shaped parts from it, with the split and the leakage drop as traced steps — and the hand-off note names that invocation. Alternative partitions are described, not materialized.

## Publish, brief, remember, summarise

**Publish the artifact.** `<out>` is the product, and the user sees it before reading about it: with validation and the smoke test passed (a non-strict smoke run without a browser counts, and the publish line then says the render is unverified), open the file in the conversation — through the runtime's artifact or file tool when it has one (the file is self-contained by the platform's contract, so it renders as it is), otherwise by delivering the file so it renders inline — and say in one line that the *Geometry* tab is the new one and what it shows (the space, the derivation graph, the orthogonality heatmap, the partition cards). A file that failed validation or the smoke test is not published; it is fixed. There is no summary of an unpublished stage.

**Write the stage brief.** `<run-dir>/docs/forge-data-brief.md` per `vega/references/brief-contract.md`: the frontmatter with the records every number resolves to (`geometry-layer.json`, `geometry.json`), then *what this stage was for*, *what was decided* (each retyping, each orientation, each derivation kept or rejected, the partition — with the channel that settled it and the alternative), *what ran* (the exact commands with their marker lines, the engine runs), *what came out* (ambient and intrinsic dimension, basis size, verified rows per rule — each with its `geometry.json` or layer key), *what the reader should check* (the symbolic runs), *open* (disagreements between channels, a fork abstained), *next*. Nothing the layer does not hold; every number with its key.

**Update memory.** `.claude/domain-forge-memory.md` § **Dataset stances**: one line per retyping, orientation and partition decided (date, dataset, the fact), plus the dataset path and output path.

**Summary.** Open with the published artifact (its path, the new tab) and the brief's path; then the run directory, the dimensions in one line, the basis and its size against the intrinsic dimension, the derivations with their provenance counts, the disagreements, the partition (chosen or the candidates), validation and smoke results, memory updated, and the hand-off: `/data-lens <out>`, or `/dataset-shaper <out> --target <label>` when the analysis is not wanted; and, when LaTeX and `document-project` are present, the documentation option in one line: `/document-project vega <lane> forge-data` for this stage's chapter. Stop.

## Failure modes — do not

- Do not let a correlation, a rank deficit, or an FD *become* a derivation on its own. The empirical channel establishes that a column is derivable; the rule that derives it, and the direction of a symmetric derivation, are yours to state and the reasoner's to verify.
- Do not report a rule as symbolically verified without a `run_query.py` result behind the number. Check `ke-vocabulary.md`'s *Not implemented* list before choosing SWRL; string, date, and list operations go to Horn, and what no engine can run is `untested`.
- Do not report an insight that `describe()`/`corr()` would give. "`total` and `subtotal` are highly correlated" is noise; "`subtotal` is definitionally `total × (1 − discount/100)`, so it is not a dimension and using both as features doubles a single direction" is the report.
- Do not resolve a fork by picking the column named `target`, `label`, or `y`. Names are semantic evidence for a *hypothesis*; the label candidate must still be one step 4 admits — a kept rule's head whose body is in the basis, or a column an exact functional dependency determines. The apply refuses any other candidate (`ERROR:`), unless the user named it: then the candidate carries that stance in `stance` (`user: …`) and the apply accepts it with a `WARN:` that it stands by the stance only. An unattended run's `unattended: …` hypothesis (step 4) never makes a choice: it stands only in an abstained partition, and a stance you write in someone else's name is the silent pick this rule forbids: `user:` quotes what the user typed or said in this run (or a memory line recording it), and `lane:` belongs to the verification harness running a registered lane — never to a run that finds a lane registry on disk.
- Do not rotate the basis (PCA, ICA) to make it orthogonal unless asked; report residual dependence instead. A named basis with known dependencies beats an orthogonal one nobody can read.
- Do not compute in the render script what the script already computed: the explorer filters, projects and joins the shipped numbers. Recomputing rank or PCA in JS would let the two faces of the artifact disagree — and do not write or edit the renderer, or append the layer by hand; `apply_geometry_layer.py` is the only writer.
- Do not summarise a stage whose HTML was not published or whose brief was not written: the run directory is evidence, the layered HTML is the product, the brief is the story `/document-project` needs — a stage that leaves the first and not the other two is a stage `/vega` records as unfinished.
- Do not pad the consequence blocks. If a decision has no downstream consequence, say "no downstream consequence" in one sentence (`decision` carries that sentence and the block's `downstream` keeps its five fields, each saying "none" — contract §3; an effect on some fields only says "none" in the others) and move on.

## Done when

The output validates (exit 0, 13–16 included) and passes the smoke test (or the non-strict run is reported as unverified), every column that step 0 did not set aside (identities, constants, foreign keys) is either in the basis or the head of exactly one kept rule with a three-valued provenance (semantic confirmed / refuted — the model always has a view; symbolic and empirical each confirmed / refuted / untested), every disagreement between channels is a visible entry in the geometry layer, at least one partition candidate is stated with its leakage set and its consequence block, the Geometry tab's four views render and re-orienting a cycle updates the basis and the candidates without a re-run, the layered HTML was published in the conversation and `docs/forge-data-brief.md` is written with every number resolving to its record, memory holds the stances, and `/model-chat` on the file can answer "which properties are primitive and which are derived, and from what" from the engines alone.
