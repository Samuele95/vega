# vega-pack contract — the bundle, the predictor, the round trip, the model card, the `bundle` layer

`/vega-pack` turns the evaluated network into something that **runs without any skill installed**: a directory that takes raw rows in the shaped dataset's *input* schema (the columns the shaper's recipe consumed, before any step), applies the recipe's fitted transformations, runs the network, and returns predictions — and proves it by reproducing `/vega-eval`'s stored predictions on the test rows. The bundle is the truth of "use": `predict.py` is the one entry point, the notebook and the REST scaffold call it, the exports are checked against it, and the model card documents what it is.

Two things drive how a bundle serves, and both are resolved once, at pack time, and written into the manifest: the **reading** (what the head's outputs mean — ten readings cover every task kind, §2.1) and the **sample shape** (what one answer is computed from — a row, a window, or a node or graph of an inference graph, §2.2). The predictor, the HTTP contract, the CSV answer, the monitor, the bundle's tests and the service's self-test all read those two records; none of them re-derives the task. `scripts/catalog.json` is the machine copy of the tables below, and `scripts/tests/test_catalog_sync.py` fails when the two diverge.

Beside the tree, the stage leaves two files it does not pin and the bundle's code never reads: `markers.json` (the pack run's `OK:` / `WARN:` / `ERROR:` / `FORK:` lines) and `bundle-layer.json` (the layer's authoring file, §8).

**The slice is resolved by role, never by a fixed file list.** `pack.py` reads `blueprint-map.json` and copies, for each role the serving slice needs (`FeatureTransformer`, `Model`, `ModelStore`, `Predictor`, `Monitor`, plus `domain.py` and `ports.py`), the file the map names — wherever the blueprint put it (`nets/`, `registry/`, `monitoring/` are as legitimate as `model/`); role-bearing files the slice leaves out (`baseline`) become `out of scope: <reason>` in the copied map; a rendered adapter is marked `implemented`; the one adapter a bundle may carry as a still-raising stub is a `Monitor` whose blueprint port does **not** say `"filled_by": "/vega-pack"`, packed without a monitor plan, marked `pending: /vega-pack — the adapter was not rendered` (every other port of the slice — `FeatureTransformer`, `Model`, `ModelStore`, `Predictor` — is always rendered and `implemented`); a blueprint whose Monitor port says `filled_by: /vega-pack` — every blueprint the forge's emitter admits — names this stage as the one that fills it, and `pack.py` without `--monitor-plan` refuses it before a file is written (`ERROR: the blueprint's <port> port (role Monitor) says filled_by /vega-pack, and no --monitor-plan was given …`, exit 2; `monitor_pack.refuse_unfilled`), so the port the blueprint gave this stage never ships as the forge's stub; every copied file's digest is checked against the ledger's `code_digests` (an altered file does not ship); the bundle's entry points import each adapter by role through the map, never by a hard-coded module path; the raw input path is resolved from the campaign root (`<root>/vega-runs/<ts>`); `mark_entrypoints` runs *after* `write_serving`, from `pipeline.json.entrypoints`, and pins the pipeline digest (the forge's pin kept as `emitted_against`). `fitted.json` ships as a **serving projection** — only the keys the emitted `preprocess.py` reads; the row-membership indices (`__split__`, `__split_raw__`, `__removed_rows__`, the split and dedupe steps' index lists — the sealed test part's membership) never leave the campaign, and the source file's digest goes to `MANIFEST.chain.shape.fitted`. The projection holds in a `full` bundle too: its `train.py` and `evaluate.py` read the fitted file beside the shaped parts they are given (`--shaped`), never the bundle's, so no shape of bundle needs the membership and none ships it. For the same reason the graph reference files carry dense `ref` ids and no raw position: train ∪ valid positions would reveal the test part's membership by complement. What a graph bundle does carry is the inference graph itself — the train ∪ valid rows' shaped features (and, for `key_pair`, their raw keys) — because an inductive answer is computed through it: someone holding both the bundle and the raw data could match those rows, so `graph/graph.json.notes` says the bundle carries the shaped features of the training and validation rows, and a graph bundle is shipped only where that content may go. `schema.json.range_seen` is computed on the **train part's finite values only**, with the non-finite count stated; `schema.json.label.decode` records the recipe's own raw → class pairs read off the train part, so no caller repairs labels; the schema and the manifest are written with `allow_nan=False` (a bare `Infinity` token is not JSON). `requirements.txt` pins public releases (a local build such as `+cu130` goes in a comment). The round trip compares **every head column** — every `compared` pair of the output record (§2.1), the per-row score included where the reading has one — plus every `decided` field against the evaluation's own decision (`columns_compared`, `decisions_compared` in the record), never a single `score` column.

**The bundle carries no story and no report.** The narrative, the report PDF and everything the demonstration page shows beyond the service's own answers are `/vega-show`'s, written into `showcase/` after the bundle exists; the bundle pins nothing of them, so documenting or presenting a bundle never changes it. `pack.py --story-plan`, `--report-aux` and `--report-pdf` answer `ERROR: --story-plan moved to /vega-show (vega-show/SKILL.md); the bundle carries no story` (exit 2).

**The two shapes (`--include`).** `serving` (the default) is the tree above: the serving slice, and `predict.py` as the one entry point. `full` copies the **whole** emitted package instead — `ingestion/`, `training/`, `evaluation/` included — and writes `train.py` and `evaluate.py` beside `predict.py`: the complete server-side system as code, for a user who will re-fit the network on their own data rather than only call it. Three things are true of `full` and must be said rather than assumed. The seal travels with the door: `ingestion/data.py`'s `load_part` refuses the test part in the bundle exactly as it does in the chain, and `load_sealed_part` still wants a `test_seal.json` and its token, so a full bundle cannot quietly re-score the held-out part. `train.py` is a composition root, not `/vega-train`: one run of one spec on shaped parts the caller names — no ladder, no ablations, no diagnostics, no HPO, no ledger, and nothing it produces carries the chain's provenance. And the round trip, the twin check and the digests prove the same thing in both shapes — the serving path — because that is what they test; a `full` bundle is not more proven, it is more complete. The manifest records which shape was built as `include`, the model card says it in Identity, and the port map differs accordingly: in `serving` the three dropped packages' ports are `out of scope: <reason>`, in `full` every port is `implemented` and the conformance gate runs without `--bundle` — in either shape, the Monitor without a monitor plan excepted: its adapter is the forge's still-raising stub, mapped `pending: /vega-pack — the adapter was not rendered`, never `implemented`.

Beside the records the sections below define, the manifest carries `package` (the emitted package's name), `label` (the partition's label), `include` (`serving` | `full`), `model_version` (the weights digest the checkpoint carries — the version every answer reports), `roles` (every pinned file by role — `code`, `data`, `example`, `record`, `build` — which `predict.verify(bundle, roles)` and the service's closed world read), `entrypoints` (the bundle's CLIs then every served file, in pack order: what `bundle_manifest.check_entrypoints` refuses to list when the bundle lacks it, and what the map names as entrypoints), `records` (the six layer records), `monitor` (with a monitor plan: the reference file and its schema, the number of checks and their kinds, the usage line, and the pack-time smoke of the monitor on train and valid), `chain.shape.fitted` (the projection record: the source file's digest, the shipped file's, the kept and dropped keys and why), `examples.demo` (the demonstration sample's record, §7.4) and `examples.context_rows` for a window bundle. The v2.2 keys of `output` — `kind`, `threshold`, `threshold_source`, `classes`, `fields` — keep their meaning and types (the model card reads `threshold` as a number and `fields` as names); every other key of `output` is new in `vega/output@2`, and `sample` is a new top-level key. A multiclass or ordinal output records `threshold: null`, because no threshold applies; `threshold.json.applies == false` gives `threshold: null` for any reading.

### 2.1 Readings — `MANIFEST.output` (`vega/output@2`)

**Resolution.** At pack time the spec's `task` resolves to one of ten **readings**. The rules are tried in order and the first match wins; `head_out` is `params.out` of the spec's last `head` block and `loss` is `spec.loss.name`. A `sequence-*` kind reads as its base, which is `task.base_kind` (a v2.2 spec without it falls back to the head: one output is `binary`, a `bce_with_logits` loss or a `task.label_format` is `multilabel`, otherwise `multiclass`; a `cumulative_link` loss is `ordinal`, otherwise `regression`), and the base is then resolved through R1–R6 with the same spec, so a regression base under a quantile loss reads as `quantile`. A kind no rule matches is refused: `ERROR: task.kind <k> has no serving reading` (exit 2).

| rule | `task.kind` | condition | reading | `base` |
|---|---|---|---|---|
| R1 | `binary` | — | `binary` | — |
| R2 | `multiclass` | — | `multiclass` | — |
| R3 | `multilabel` | — | `multilabel` | — |
| R4 | `ordinal` | — | `ordinal` | — |
| R5 | `regression` | `loss == quantile` and `head_out > 1` | `quantile` | — |
| R6 | `regression` | — | `regression` | — |
| R7 | `unsupervised` | — | `reconstruction` | — |
| R8 | `anomaly` | `loss == svdd` | `anomaly-svdd` | — |
| R9 | `anomaly` | — | `anomaly-reconstruction` | — |
| R10 | `sequence-classification` | base ∈ `binary`, `multiclass`, `multilabel` | the base's reading | `task.base_kind` |
| R11 | `sequence-regression` | base ∈ `regression`, `ordinal` | the base's reading | `task.base_kind` |
| R12 | `forecast` | — | `forecast` | `regression` |

**Readings.** One row per reading. `link` is the one link vocabulary of the chain (`vega-forge/scripts/catalog.json` `inspection.links`; `network-view@2 task.link` uses the same values), and the reading → link column below is the table `inspection.links` holds: vega-pack's `test_catalog_sync` fails when the two map a reading differently. Fields are named by pattern; the placeholders are listed below the table. Every record's `fields` also carries the shape's own fields: `graph_id` first at graph level (kind `group`), `answered` before `warnings` for a window shape (kind `answered`), and `warnings` last, always (kind `warnings`).

| reading | link | decision | fields (in order) | compared (bundle ← stored) | decided (bundle ← source) |
|---|---|---|---|---|---|
| `binary` | `sigmoid` | `threshold`, probability scale: `p_<positive> ≥ threshold` | `label`, `p_<class>`, `score` (the raw logit), `prediction` (0 or 1) | `score ← score` | `prediction ← prediction` |
| `multiclass` | `softmax` | `argmax` | `label`, `p_<class>`, `logit_<class>` | `logit_<class> ← score_<k>` | `label ← argmax` |
| `multilabel` | `sigmoid_each` | `per-label-threshold`: `p_<label> ≥ t_<label>` | `p_<label>`, `logit_<label>`, `pred_<label>` | `logit_<label> ← score_<k>` | `pred_<label> ← threshold` |
| `ordinal` | `cumulative` | `cumulative`: `Σ_j [σ(z_j) ≥ 0.5]` (`decision_rule: cumulative_count`) | `label`, `p_<class>`, `cum_<cum>` (`P(y > <cum>)`), `logit_cum_<cum>` | `logit_cum_<cum> ← score_<k>` | `label ← cumulative` |
| `regression` | `identity` | `none` | `value` | `value ← score` | — |
| `quantile` | `identity` | `none` | `value` (the 0.5 quantile, when 0.5 is one of Q), `q_<q>` | `q_<q> ← score_<k>` | — |
| `forecast` | `horizon` | `none` | `value_h<h>`, or with quantiles `value_h<h>_q<q>` (horizon-major) | `value_h<h> ← score_<k>`, `value_h<h>_q<q> ← score_<k>` | — |
| `reconstruction` | `reconstruction` | `none` | `reconstruction_error`, `recon_<feature>` (or `out_<k>` when the head is wider than the input features) | `recon_<feature> ← score_<k>`, `out_<k> ← score_<k>`, `reconstruction_error ← row_score` | — |
| `anomaly-reconstruction` | `reconstruction` | `threshold`, score scale: `score ≥ threshold` | `score`, `prediction`, `label` (labelled tasks only), `recon_<feature>` or `out_<k>` | `recon_<feature> ← score_<k>`, `out_<k> ← score_<k>`, `score ← row_score` | `prediction ← prediction` |
| `anomaly-svdd` | `distance` | `threshold`, score scale: `score ≥ threshold` | `score` (`‖f(x) − c‖²`), `prediction`, `label` (labelled tasks only), `emb_<j>` | `emb_<j> ← score_<k>`, `score ← row_score` | `prediction ← prediction` |

Placeholders: `<class>` is each name of `classes` in spec order (binary: `[negative, positive]`); `<positive>` is `str(task.positive)`, else the last class, else `"1"`; `<label>` is each label of a multilabel task; `<cum>` is each cumulative threshold class `c_j`, `j < K−1`; `<q>` is each quantile of `loss.params.quantiles` written `format(q*100, "g")` with `.` replaced by `p` (0.1 gives `q_10`, 0.025 gives `q_2p5`), and `<median>` is the one nearest 0.5; `<h>` is each horizon step `1…H`; `<feature>` is each FeatureContract column, numeric then nominal; `<j>` is each embedding coordinate; `<k>` is the stored score column index (horizon-major for an `(H, Q)` head), and `score_<k>` is the single column `score` when `head_out` is 1.

**Semantics that are not negotiable.** Binary and multilabel scores are logits and the sigmoid is applied unconditionally: the binary `score` field *is* the raw logit, `p_<positive>` is the probability, and a row's decision never depends on the other rows of the batch. The ordinal probabilities are `P(y=c_0) = 1−σ(z_0)`, `P(y=c_j) = σ(z_{j−1}) − σ(z_j)`, `P(y=c_{K−1}) = σ(z_{K−2})`, clipped at 0 and renormalised — a row that needed clipping carries the warning `cumulative logits not monotone; class probabilities clipped`. The quantile head's layout is horizon-major, `(B, H, Q)`. The anomaly threshold is on the score's own scale, never squashed. Every reader of the reading's semantics goes through the backend's `TaskReadout`; `serve/` holds no per-task code.

**The record's keys.** `schema` (`vega/output@2`), `kind` (`task.kind` verbatim), `reading`, `base` (the base kind for `sequence-*` and `forecast`, else null), `link`, `decision` (`threshold | argmax | per-label-threshold | cumulative | none`), `head_out`, `classes` (class readings and labelled anomaly: the class names; multilabel: the label names; else null), `positive`, `threshold` (number or null), `threshold_source` (`valid-optimum | vega:default | user:<turn> | null`), `threshold_scale` (`probability` for binary and multilabel, `score` for the anomaly readings, else null), `threshold_per_label` (multilabel: `{label: number}` when `threshold.json` carries `per_label`), `quantiles`, `horizons`, `fields` (the concrete names, in order), `field_kinds` (every field → `{kind, of}`, §7.3), `compared` (`[bundle field, stored column]` pairs), `decided` (`[bundle field, source]`, the source a stored column or one of `argmax`, `cumulative`, `threshold`), `score_field` (the one field the automatic `output_psi` check reads: the first of the reading's `score_field` patterns present in `fields` — `p_<positive>` for binary, `value` then `q_<median>` for quantile, `value_h1` then `value_h1_q<median>` for forecast — or null for `multiclass`, `multilabel` and `ordinal`, whose output checks read the decisions), and `truth`.

**Truth.** `truth = {"column", "type", "sep"}`: `type` is `class` for the class readings and a labelled anomaly task, `number` for the value readings, `labels` for multilabel — one shaped column of delimited names, split on `sep` (from `task.label_format`) — and `truth` is null for `reconstruction` and an unlabelled anomaly task.

**Refusals.** Every `compared` and `decided` bundle field must be in `fields`, and every field must match a pattern of its reading; pack refuses otherwise (exit 3). Two class, label or feature names that read as the same field name are refused (exit 2: the fields are not unique). A `threshold.json` on another scale than the reading decides on (`probability` for binary and multilabel, `score` for the anomaly readings) is refused (exit 2, re-run `/vega-eval`). A sample record with an unknown shape or a window `length` below 2 is refused (exit 2). A row-score reading whose stored predictions carry no `row_score` is refused before the round trip (§5).

### 2.2 `MANIFEST.sample`

Every bundle records its sample shape; `/v1/info` publishes it and the predictor assembles batches from it.

```json
"sample": { "shape": "row" }

"sample": { "shape": "window", "length": 24, "stride": 1, "horizon": 3,
            "series_by": "station", "order_by": "ts", "context": "previous-part", "autoregressive": true,
            "lag_depth": 2, "history_rows": 25,
            "rule": "each row is a window end; answered when length-1 preceding rows of its series exist in history + rows" }

"sample": { "shape": "graph", "level": "node", "protocol": "inductive", "method": "knn",
            "directed": false, "self_loops": true, "graph_id": null,
            "reference": { "parts": ["train", "valid"], "nodes": 1840, "edges": 9120,
                           "files": { "nodes": "graph/reference-nodes.parquet", "edges": "graph/reference-edges.parquet", "meta": "graph/graph.json" } },
            "rule": "messages flow reference -> query only; an answer does not depend on the other rows of the request" }
```

- **Window.** Each request row is a window end (its anchor). A row is answered when the `length − 1` rows preceding it *in its own series* exist in `history` plus the earlier request rows; otherwise it is answered `answered: false` with a warning, and one row out per row in, in the order given, stays true. `stride` thins training anchors only; scoring is dense, one answer per scorable row. `series_by` and `order_by` are honoured, so a request may hold several series and each gets its own history. `horizon` and `autoregressive` are present for `forecast` only; an autoregressive forecast takes the target column's past as an input channel, so the target column is required in `rows` and `history` (§3). `lag_depth` is the largest lag of the recipe's `lag` steps (0 without one) and `history_rows = (length − 1) + lag_depth` is what a caller sends so that every row is answered with a fully determined lag context. `context` is the forge's `defaults/window_context` (`previous-part` or `none`).
- **Graph.** The **inference graph**: reference nodes are train ∪ valid, with every edge among them; query nodes receive messages from reference nodes only — no query → reference and no query ↔ query edge — so an answer never depends on the other rows of the request. At node level each request row is a query node, attached by `edges_for`; at graph level a query is a whole graph, its within-graph edges (`edges_within`) all kept, and the raw `graph_id` column says which rows form it. Only `protocol: inductive` is served: a transductive graph is refused at pack, `ERROR: transductive graph protocol: the served answers would depend on the fixed deployment graph; /vega-pack v2.3 serves inductive graphs only` (exit 2). `history` is refused for a graph (422).

### 2.3 Graph reference files — `vega/graph-reference@1`

Written for a graph sample shape only, role `data`, pinned in `MANIFEST.files` like every data file — a tampered `graph/reference-nodes.parquet` is refused by `predict.verify()` before anything runs.

- `graph/reference-nodes.parquet`: one row per reference node — `ref` (int64, dense `0…R−1`: the train rows first, then the valid rows, each in split order), every FeatureContract column as shaped, and for a `key_pair` graph the raw key columns the edges are built from. **No raw position ships.**
- `graph/reference-edges.parquet`: `src_ref`, `dst_ref`, `weight` (a float, or null for an unweighted method) — the edges among reference nodes, mapped to `ref` ids.
- `graph/graph.json`: `{"schema": "vega/graph-reference@1", "method", "params", "level", "directed", "self_loops", "symmetric", "protocol", "parts": ["train", "valid"], "n_nodes", "n_edges", "feature_columns", "edges_for_columns", "notes"}`. `edges_for_columns` is the set the shaped manifest names, in the order the emitted transform's `EDGES_FOR_COLUMNS` reads them (pack compares the two as sets; the Predictor compares graph.json with the transform at load). `notes` always says the bundle carries the shaped features of the training and validation rows and the input columns its graph step reads, and that no raw position ships; above 1,000,000 reference nodes pack also prints `WARN:` with the count and records it there — there is no hard cap.

### 2.4 The serve record — `MANIFEST.serve`

Written by pack whenever `serve/` is rendered (§7). Beside the v2.2 keys (`present`, `mode`, `framework`, `entry`, `endpoint` — `"POST /predict"`, the v2.2 alias route the online app still answers, `null` for a stream consumer — `identity`, `image`, `run`, `source`) and `demo_sample` (`{per_stratum, file, presets}` when a demonstration sample was drawn) it carries:

- `endpoints` — the sorted `"METHOD /path"` list of the route modules whose capability is enabled in this bundle, read from their `ENDPOINTS` literals (§7.2); never a hand-written list. It is spelled as the framework registers the routes, so the showcase file route reads `GET /showcase/{path:path}` here, while `showcase_slot.routes`, the catalogs and the blueprint declaration (§2.6) spell it `GET /showcase/{path}` — the `:path` converter is the framework's, not the API's, and every comparison between the two lists reads `{path:path}` as `{path}`. A stream bundle has `endpoints: []`: its consumer serves no HTTP route.
- `templates` — `{"backend", "digest": "sha256:<over the sorted template files>", "files": {name: digest}}`: every template file the `serving_templates` patterns name (§7.1), by digest, and the digest of that listing — what `--re-emit-serving` compares (§7.8). The `docker/` and `readme/` fragments the Dockerfile and the README are assembled from are not template files of a pattern and are not in it.
- `forced_by` — `"--serve"` when `--serve` rendered the online adapter over a `batch` or `stream` blueprint; `mode` is then `"online"` and the divergence is recorded against the blueprint. Absent otherwise.
- `showcase_slot` — always, whenever `serve/` is rendered, and exactly: `{"dir": "showcase", "schema": "vega/showcase@1", "routes": ["GET /", "GET /console", "GET /showcase/{path}", "GET /v1/story", "GET /report.pdf", "GET /v1/showcase"], "env": "<ENV>_SHOWCASE", "flag": "--showcase"}` (§7.6).
- `inspection` — `{"schema": "vega/inspection@1", "enabled", "weights": "full" | "summary", "network_schema": "vega/network-view@2", "explanation_schema": "vega/explanation@2", "files": [the package-relative inspection files], "block_types": [the block types of this spec], "opaque": [node ids], "chain", "network_digest": {"full", "summary"}, "self_test", "source": "vega-forge/references/inspect-contract.md"}`, written after the pack-time inspection check passed (§7.7).

The v2.2 `story` key is gone; a batch bundle without `--serve` has `serve.present: false` and none of the above except `inspection`, which is written in every mode that carries the Predictor's module (§7.7): a batch bundle's `load_inspector` verifies the same `network_digest` pin, and only `--no-inspect` ships a bundle without it (`enabled: false`, no `inspection/`).

### 2.5 `MANIFEST.reemits`

A list, empty at pack time; every accepted `--re-emit-serving` appends `{"at", "reason", "previous_manifest_digest", "templates_digest", "changed": [...]}` (§7.8).

### 2.6 `MANIFEST.blueprint`

`{"run": <the pipeline.json packed against>, "map": "blueprint-map.json", "conformance": {…}}`. `conformance` is the mechanical half of the gate `pack.py` ran (`code-contract.md` §5): `mechanical` (`pass`, `fail` with `why`, or `not run` with `why` when no `--pipeline` was given), `checks` (the number of `OK:`/`WARN:`/`ERROR:` lines the gate printed — a count of check results, not of the rules C0–C14), `include`; `architect` is `null` — the judgement half runs through the Skill tool after `pack.py`, and the bundle layer records its result and its advisory outcome (§8); a count typed here is a malformed record the apply script refuses. With a served HTTP surface it also carries the declaration fork's record (§7, *What the blueprint must record*): `api_declared` (true only when every served endpoint is a declared bet of the blueprint) and `declaration` — `{"pipeline", "served", "missing", "answer": "declared" | "open" | "extend" | "divergence", "source", "by_default", "targets": {<extends target>: [{method, path, capability, calls}]}, "extends": "/blueprint --extends …", "note"}`, plus, whenever an endpoint is missing, `targets` (each missing endpoint under the `/blueprint --extends` target it belongs to) and `extends` (the call that would declare them — the one the unattended answer `extend` applies); `by_default` names the endpoints an earlier unattended run declared as `vega:default` bets. A stream or batch bundle serves no HTTP endpoint and has no declaration.

## 3. Preprocessing in transform-only mode, and the input schema

The shaper's `reproduce_<slug>.py` re-executes the whole recipe from the input path — it splits and it fits. Inference needs the recipe **applied to new rows with the parameters already fitted**: `<package>/<features module>/preprocess.py` (the `FeatureTransformer` adapter, in the module the map names for the role — `features/` in the default layout; the entry point imports `<package>.<features module>.preprocess`) is generated by `dataset-shaper/scripts/shape.py --transform-only --recipe recipe.json --fitted fitted.json --emit <package>/<features module>/preprocess.py` (a shaper capability this contract requires — see the patch to dataset-shaper, `shape-contract.md` §2, which owns the semantics: which ops are applied, which are skipped, the reserved `unseen_category_id` per encoded column from the manifest, the byte-for-byte twin check) and exposes `transform(df_raw, history=None) -> df_shaped` (the `FeatureTransformer` Protocol, satisfied structurally); a graph recipe also exposes `edges_for(df_raw, reference)` (query → reference edges, raw rows in, the reference's `ref` treated as an opaque node id) and, at graph level, `edges_within(df_raw)` (the edges between rows of the same `graph_id`). Before the bundle's own round trip, `pack.py` runs the shaper's twin check, `verify_shape.py --transform-only`, on the test part's raw rows — the only test of `preprocess.py` that does not go through the network — and records its result in the manifest's `roundtrip.shaper_transform_check`.

`schema.json` is derived from the recipe's `input` (the raw columns the first step consumed, with the geometry's types) and from the shaped manifest (what each becomes): `{ "input": [ { "name": "zip", "dtype": "string", "required": true, "allowed": "<categories seen in train, or 'any'>" }, { "name": "unit_price", "dtype": "float", "required": true, "range_seen": [0.5, 199.0] } ], "output": { "label": "…", "p_<class>": "…", "score": "…", "prediction": "0|1 at threshold 0.41" }, "truth": { "column": "late", "type": "class", "sep": null }, "ignored": ["late", "order_id"] }`. `predict.py` validates rows against it — the label column and the identity columns are optional in the input and ignored when present (`schema.ignored`), a missing feature is an error — and reports out-of-range values as warnings (a value outside the training range is not an error, but the model card says extrapolation is unmeasured).

- **`output`** describes one entry per field *pattern* of the reading (`"p_<class>"`, `"q_<q>"`, `"value_h<h>"`, `"recon_<feature>"`), taken from the catalog's `output_readings.<reading>.describe`, so every served field is described and no description is written twice.
- **`truth`** is `MANIFEST.output.truth` copied: the column a caller may send to the monitor, held to its type — a class, a number, or labels split on `sep`.
- **Graph level:** the raw `graph_id` column is listed in `input` with `required: true` and `dtype: "string"`, and is not ignored — it is what groups a request's rows into graphs.
- **Window:** `"sample": {"history_rows": n}`, so `/v1/schema` says how much history a caller sends; for an autoregressive forecast the target column is listed in `input` with `"role": "autoregressive"`, required in `rows` and in `history`.

## 4. `predict.py`

Module API (`<package>.serving.predict`, the `Predictor` adapter; re-exported by the bundle's `predict.py`): `Predictor(model, transform, records, context=None)` — `model` the network as the blueprint's Model port, read through its `head` and `anatomy()` alone (a model in training mode, of another spec, or with no anatomy is refused), `records` the serving records read from the manifest and the schema (`vega/output@2`, the sample record, the versions), `context` the graph context of a graph bundle, else None. `Predictor.predict(df_raw: DataFrame, history: DataFrame | None = None) -> DataFrame` returns one row per input row, in the order the rows were given and under the caller's index (row *i* of the answer is input row *i*'s: a window request holding several series in any order is answered row for row, never grouped by `series_by` nor sorted by `order_by`; the HTTP `predictions` list follows the request's `rows` the same way), with the output record's `fields` (the answer, per reading, decided through the backend's `TaskReadout`, `answered` for a window shape, and `warnings` per row); `Predictor.predictions(df_raw, history=None)` the same as the domain's `Prediction` values (the class, its probabilities in class order — the record's `probability` fields, the readout's distribution; none for a value reading or a row without a decision —, the raw head, the versions); `Predictor.predict_one(row: dict, history=None) -> dict`; `Predictor.info() -> MANIFEST`; `Predictor.prepare(df_raw, history=None) -> Prepared` — the only raw → batch path, `(batch, shaped, sample_of_row, index, warnings, n_samples)`, what the inspection machinery explains through; and the read-only `model`, `reader` and `records`. The Predictor module holds that one class, `_prefixed` helpers, imports and constants — no public `build()` and no second public class.

The bundle's `predict.py` exports `load(bundle_dir=None) -> Predictor` (verify, then the recipe, the spec, the weights through the store, the records, and for a graph bundle `load_context`), `load_context(root, recipe_module)` (the graph reference, verified with the `data` role), `load_monitor(bundle_dir=None)`, `load_inspector(bundle_dir=None)` (the inspection facade, when the bundle carries it), `check_examples(bundle_dir=None, predictor=None) -> dict` (rows.csv through `predict`, compared at `expected.__row__` over the compared fields at the round-trip tolerance and exactly over the decided fields, no unanswered row among them — the one example comparison the bundle test, the service's self-test and the notebook all call), `predict`, `read_rows`, `verify(bundle_dir=None, roles=("data",))` and `bundle_root`. CLI: `python predict.py --bundle . --input rows.csv --output preds.csv [--format csv|parquet|json] [--history <file>]`, `--one '{"zip": "60614", …}' [--history <file>]`, `--check` (runs `check_examples` and the digests). The predictor runs the network in inference mode (the store loads it in eval mode, and the Predictor refuses one in training mode rather than switch it), seeds nothing (inference is deterministic), never writes outside `--output`, never reaches the network, and imports only the bundle's own files and `requirements.txt`.

With `--include full` two more entry points sit beside it, each a thin composition root over the package's own adapters and neither a re-implementation of the stage it echoes. `train.py --shaped <dir> [--out <dir>] [--epochs n] [--budget min]` builds the network through `model/network.py`'s `build_model`, fits it through `training/loop.py`'s `fit` against the parts `ingestion/data.py` loads from `<dir>`, and checkpoints through `model/store.py` — one run of `netspec.json`, printing the per-epoch record and writing `best.pt` and `history.jsonl`. The shaped parts do not travel with the bundle, so `--shaped` is required and the bundle refuses rather than guessing; `recipe.json` is what makes new ones, through the chain's shaper. `evaluate.py --part valid [--shaped <dir>] [--weights <file>]` scores a part through `evaluation/evaluate.py` and prints the metrics the spec names. `--part test` needs `--seal <test_seal.json>` and `--token`, and without them it refuses with the same words `load_part` uses — the bundle inherits the seal, it does not escape it.

## 5. The round trip (`tests/test_roundtrip.py`)

Two checks, and the first is not optional. **At pack time**, `pack.py` recovers the raw rows of the whole test part (by `row_id` from `predictions.test.parquet`, the raw file's row positions) and asserts that `predict` on them equals the stored predictions within the **round-trip tolerance** — `|Δ| ≤ 1e-6 · max(1, max|score|)` for an fp32 checkpoint (absolute near zero, relative for large regression values), the backend's declared inference tolerance for a reduced-precision checkpoint — row by row, for every test row, whatever `--examples` says — the proof that *raw rows → preprocess → network* in the bundle equals *shaped test rows → network* in the evaluation. Every `compared` pair of the output record is compared numerically at that tolerance, and every `decided` field exactly against the evaluation's own decision (its stored `prediction`, or the argmax / cumulative count / per-label threshold of its stored scores); an unanswered row at a stored position is itself a failure. Running the network on the test rows here exposes nothing: the outputs are compared to the stored ones and discarded, no metric is computed, the seal is not touched.

**What the evaluation stored** is `vega-eval/references/eval-contract.md` §2's (`vega/predictions-layout@1`), read here only through vega-eval's own reader, `predictions_layout.read`, never re-parsed. Every stored prediction is paired with the bundle's answer by `row_id` (the row's, the window anchor's or the node's raw position) — by `graph_id` at graph level — never by position and never re-mapped. A row-score reading whose stored layout has no `row_score` is refused before the round trip: `ERROR: the evaluation stored no per-row score for a <reading> head; re-evaluate with vega-eval v2.3` (exit 3). A graph bundle whose emitted `preprocess.py` lacks `edges_for` (at graph level, `edges_within`) is refused (exit 3).

**Per shape.**

- **Row:** the test rows, each paired with its stored prediction by `row_id`. For a recipe with `lag`, the rows go with the empty history window the shaper's twin check runs with (the evaluation's parts were shaped with their lags restarting).
- **Window:** per series, `history` is the last `history_rows` rows of the previous parts — train then valid, in `order_by` order, as the evaluation borrowed its context — under `context: previous-part` (none under `context: none`), the query is the series' test rows (a series and its order are read off the Recipe's own output for the key columns, as the evaluation read them), and answers are compared by `row_id` (the anchor). The stored count is `len(test) − |unscored|`. A recipe with `lag` restarts its lags at each part start in the evaluation, while a served answer reads its lags from the history, so the first `(length − 1) + lag_depth` test rows of each series are excluded from the comparison and recorded in `MANIFEST.roundtrip.boundary = {"rows": n, "reason": "lag restarts at the part start in the evaluation; served answers read the history"}`; with `lag_depth == 0` nothing is excluded and the comparison is exact.
- **Graph, node level:** the whole test part as queries against the reference (§2.3), in chunks of 4096 query rows — legal because an answer does not depend on the other rows of the request; attachment edges come in `edges_for` order, so node-level answers are held to the round-trip tolerance, never to bit equality.
- **Graph, level graph:** the test rows grouped by `graph_id`, one answer per graph, compared by `graph_id`.

`MANIFEST.roundtrip` records `rows` (every stored prediction, boundary rows included), `source`, the tolerance with its `scale` (`max(1, max|score|)`), `max_abs_diff`, `columns_compared`, `decisions_compared`, `status` and `shaper_transform_check`. **Refusals, exit 3, before any layer:** a row-score reading without `row_score` (above); a stored layout other than `@1` or without `row_id`; a compared column the stored predictions lack; a window evaluation without `unscored.json`, or whose stored count is not the test part's scorable windows; a graph-level evaluation without `graph_id`, or whose graphs are not the test part's; a graph Recipe without `edges_for` / `edges_within`; and the comparison itself — `the bundle does not reproduce the evaluation's predictions`, naming the first differing row, the column and the recipe step suspected, with `— a decided field disagrees with the evaluation's decision` when the difference is a decision rather than a number.

**In the bundle**, `tests/test_roundtrip.py` loads the bundle and calls `check_examples`: `predict` on `examples/rows.csv` (with the context rows a window bundle ships first), compared with `examples/expected.parquet` at each `__row__` (the index of the `rows.csv` row each expected answer belongs to — an explicit key, so the comparison never depends on order; every v2.3 bundle writes it, and only a v2.2 bundle, which lacks it, is compared by position) — the stored predictions for those rows when `examples.kind` is `test`, the predictor's own outputs at pack time when it is `synthetic` (then the test proves the bundle still reproduces itself, and the manifest says which kind it is); then asserts `MANIFEST.files` digests — at the same round-trip tolerance, which the manifest records; and it proves the serving seam: with the network handed over behind a stand-in carrying the Model port's methods alone (the port `blueprint-map.json` gives the role `Model`, as the bundle's `ports.py` declares it), the examples still reproduce and the inspector, when the bundle carries one, still opens ready — the Predictor and the inspection read the network through its `head` and `anatomy()` and nothing else (`vega-forge/references/code-contract.md` §1). `MANIFEST.examples` records `compared_rows` (the rows with an expected answer) and, for a window bundle, `context_rows` (`length − 1`, the rows shipped first so the first compared window is complete); `MANIFEST.roundtrip` records `columns_compared` and `decisions_compared` (`labels_compared` is kept as its v2.2 alias) and, for a window bundle with a lag, `boundary`. The examples per shape: a row or node bundle ships the first *n* test rows (`__row__` 0 … n−1); a window bundle ships, per series from the test part's start, the `length − 1` context rows then the rows compared, series after series until *n* are compared (so its lags restart where the evaluation's did and the shipped windows reproduce exactly); a graph-level bundle ships whole test graphs until at least *n* rows, one expected answer per graph at its first row, with its `graph_id`. `expected.parquet` holds exactly `__row__`, `graph_id` at graph level, and every compared and decided field — never the stored `row_id`, a raw position of the test part. Before they ship, the test examples are answered exactly as `check_examples` answers them (`rows.csv` alone, no history) and compared at the round-trip tolerance: a mismatch refuses the pack (`ERROR: the shipped examples do not reproduce the evaluation: …`, exit 3), so a bundle whose own test would fail is never written. `examples/request.json` is one ready body for the shape: `{"rows": [first]}` for a row or a graph node, `{"rows": [anchor], "history": [its predecessors]}` for a window, the rows of one graph at graph level. A pack-time failure is a defect in `features/preprocess.py` (a step applied out of order, a fitted parameter misread) or a copied file that does not match; the packer refuses to write the layer until it passes. With `--export onnx,torchscript` (a comma list), `exports/parity.json` records each exported model's outputs against `predict.py`'s on the same rows at `atol 1e-5`.

## 6. The model card (`model-card.html`)

One self-contained HTML (no external refs; inline SVG; ≤ 2 MB), the reproducibility document a reader opens without the chain: **Identity** (slug, run, created, digests); **Task and data** (the partition and label from geometry, the source dataset's rows and columns, the shaped feature contract, the split kind and sizes, the recipe in one line per phase with sources — copied from the layers, never rewritten); **Architecture** (the blueprint map — ports, modules, boundaries and the file that implements each — the conformance result, then the decisions table with sources, the block diagram, parameter count, the loss and update rule from the mechanics reading); **Training** (the ledger table, the selected run's curves, the selection rule, budget, device, determinism tolerance); **Evaluation** (the seal and exposures, the metrics table with CIs, the baselines and paired differences, the calibration curve, the worst slices, the verdict verbatim); **Intended use and limits** (`readings.limits` from the evaluation, the ranges seen in training from `schema.json`, the stances under which it ships); **How to use** (the CLI, the module call, the REST endpoint when present, the exports). Every number in the card — the ranges-seen table from `schema.json` included — is spliced by `scripts/model_card.py` from the layers' data scripts and the bundle's records; the packer writes the prose of *Intended use and limits* only, and that prose may contain no digits (the card script refuses a number in the hand-written section, so nothing is retyped).

## 7. Serving and exports (on flag)

`predict.py` takes `--history <file>` for a window bundle and for a recipe with `lag` (the rows preceding the query, in the raw schema). `--serve` (default on for `serving.mode` `online` and `stream`, off for `batch`; `--no-serve` overrides) writes the interaction adapter the mode implies. `online`: `serve/app.py` — a FastAPI application composed of route modules (§7.2): `POST /v1/predict` (a list of rows, plus `history` for a window bundle, validated against `schema.json`, answered per reading, §7.3), `POST /v1/predict/csv`, `POST /v1/monitor`, `GET /v1/info` (an allow-list of the manifest, `sample` included), `GET /v1/schema`, `GET /v1/examples` (§7.4), `GET /v1/code`, `GET /health`, the inspection routes and the showcase slot's routes — a `Dockerfile` that installs `requirements.txt` + `fastapi`/`uvicorn`, and a README section with the `curl` example built from `examples/request.json`. `stream`: `serve/consumer.py` — a consumer loop with one pluggable `source()` iterator (a stub that reads JSON lines from stdin, to be replaced by the user's queue client) calling the predictor per batch with a history buffer of the last `history_rows` rows, so windows complete across batches, and `monitor.py` per batch, plus the same Dockerfile and README; it reuses the row contract of the online service. `batch`: nothing beyond `predict.py --input` (the CLI is the batch interface), and the manifest's `serve.present` is false. `pack --serve` on a `batch` or `stream` blueprint renders the online adapter anyway and records `serve.mode: "online"` with `serve.forced_by: "--serve"` (§2.4). The app imports `predict.py` and nothing else of the model; batch mode is `predict.py --input`. `--export onnx,torchscript` (a comma list; any subset) calls the backend's `export` and `parity` per format; a parity failure is `WARN:` in the manifest and the card (the export ships marked, never silently).

**The serving release — rules the gates established.** `serve/` is rendered from the backend's serving templates by `pack.py --serve` (flags `--demo-sample`, `--monitor-plan`, `--service-title`, `--row-noun`, `--service-description`, `--service-port`, `--no-inspect`, `--inspect-weights`); which template files render where is §7.1; the rules below were fixed by four `/architect --baseline` gates on a real lane, and a rewrite must keep them:

- **One row contract.** JSON and CSV go through the same pydantic row model; a type error names the column, never the union branch; a digit-code column (train values matching `^[0-9]+$`) refuses `80.0` and `-7`; booleans are not numbers; the truth column (`schema.json` `truth.column`) is held to its type — a class, a number, or labels split on `sep` — on both paths. `PredictRequest.history` carries a `max_length`; a body without `Content-Length` is read up to the row cap, never whole. No dataset literal lives in a shared template — title, row noun, description, command prefix and port are injected, the contract's OpenAPI text included; the bundle's tests take the env prefix from `MANIFEST.serve.identity.env`, with no fallback.
- **Code runs from where it is installed; data from the bundle directory; both verified.** The service imports `predict.py` by file from its own location and `find_spec`-checks the package's origin before executing anything; every pinned code file is verified (closed world — an unpinned module, a route module included, is refused and the service stays unready; when a file of `serve/` itself is not the packed one, the service trusts none of its own modules and answers **503 on every route**, `/health` included, with the refusal as the reason, rather than let a tampered module speak for it); the data half goes through `predict.verify(bundle, roles)`, the one implementation the CLI's `load()` / `load_monitor()` also use; `MANIFEST.roles` (code / data / example / record / build) is written by pack.
- **Every refusal is a problem+json body; an unready service answers 503 before parsing.** Start-up failures leave the service unready and never escape `create_app`; 404/405 carry problem bodies; `/v1/monitor` without a reference is 404. The paths answered before the self-test passed are the union of the route modules' `OPEN_WHILE_UNREADY` (§7.2), so a page can load and say "not ready".
- **Versions on every answer** — `model_version` (the weights digest carried inside the checkpoint), `contract_version` (the `schema.json` digest), `feature_contract_version` (the shaped manifest's digest) — as JSON fields and CSV headers.
- **Admission at the ASGI edge, before the body is read.** Default bound ≤ 2 in flight *per process* (`--workers N` multiplies it and the resident model: the README says so, or the default is divided by the worker count); no place → 503 Busy + `Retry-After`; `/health` stays responsive; body size → 413; the CSV parse stops at the row cap. A route module's `MODEL_ROUTES` are the admitted ones.
- **Port 8765 by default** (8000 collides with local model servers such as vLLM); the Docker base image is pinned by digest; the bundle is root-owned and read-only to the service user, no chown layer; `/v1/examples` is built once from the verified files; `/v1/info` answers from an allow-list with the campaign as an id, not a host path.
- **The monitor has a plan and a reference.** The Monitor's adapter file (the map's; `serving/monitor.py` in the default layout) is rendered from a monitor plan (`--monitor-plan`, required when the blueprint's Monitor port says `filled_by: /vega-pack` — a pack without it is refused before anything is written, exit 2): one check per `pipeline.json.monitoring[]` concern (at least one check when the blueprint names none), of a kind the bundle's reading admits (§7.5), with its reference measured on train (valid for the unseen rate, the recall and the output references); the unseen check asks the `FeatureTransformer` (`transform(..., with_unseen=True)`), never a copied vocabulary; a reading is a `DriftReading` value object (`code-contract.md` §4, EJ-34). The predictor's schema warnings apply the range check to finite values only, treat a non-finite value as news only when the schema says the column never had one (`non_finite_seen`), and flag a code column arriving as float per row.
- **What the blueprint must record** (`/blueprint --extends` amendment): `serving.api.errors` (413; 503 Busy + Retry-After; 404/405 problem bodies; 404 for `/v1/monitor` without a reference) and `serving.concurrency` (`max_inflight`, `inflight_wait`, `max_body`, admission "before body"), so that `/architect --baseline` on the bundle reads them as bets, not as divergences; the endpoints `MANIFEST.serve.endpoints` lists are compared with `pipeline.json.serving.api.endpoints`, and missing ones are declared through `/blueprint --extends serving.api | serving.inspection | serving.showcase | serving.demo` (unattended: applied, or `WARN:` and `blueprint.conformance.api_declared: false` when the blueprint skill is absent).
- **Templates are files.** Every serving template — the bundle CLI, the tests, the Dockerfile and the service — is a file under the backend's `templates/serving/`, lint-able and measured against C11–C13 like any other code; `pack.py` holds no template in a string. An unfilled `{{…}}` placeholder after rendering is `ERROR:` (exit 2).

### 7.1 Serving templates

The backend's `templates/serving/` holds four destinations. `catalog.json` `serving_templates` names them by glob pattern, so a new template file needs no catalog edit:

| destination | patterns | renders into |
|---|---|---|
| `package` | `package/*.py`, `package/inspection/*.py` | `<package>/<serving module>/` (the Predictor's module; `inspection/` below it, skipped with `--no-inspect`) |
| `serve` | `serve/*.py`, `serve/static/index.html` | `serve/` |
| `bundle` | `bundle/*` | the bundle root |
| `tests` | `tests/*.py` | `tests/` |

A pattern matches a template path relative to `templates/serving/` segment by segment: both have the same number of `/`-separated segments and each segment matches under `fnmatch.fnmatchcase`, so `*` never crosses a `/` (`package/*.py` does not name `package/inspection/codec.py`) and it does match a leading dot (`bundle/*` names `bundle/.dockerignore`). `vega_pack_core.template_matches` is the one implementation. The pattern's first segment is the destination and is replaced by it on render. Every rendered `package` file is a `kind: support` entry of the copied `blueprint-map.json`, `used_by: ["Predictor"]`; every `serve` and `tests` file is an entry point. The `stream` mode renders the consumer and the row-contract modules it reuses; `batch` renders no `serve` file.

### 7.2 Route modules and endpoints

The service is `create_app(bundle_dir=None, max_rows=None, torch_threads=None, max_inflight=None)` over a closed, ordered list of route modules, `ROUTE_MODULES = ("routes_meta", "routes_predict", "routes_monitor", "routes_inspect", "routes_showcase")`, each `serve/routes_<name>.py`. Each exports module-level literals pack reads with `ast.literal_eval`, never by importing the module:

```python
ENDPOINTS: tuple[tuple[str, str], ...]        # (("GET", "/v1/network"), ("POST", "/v1/explain"), ...)
MODEL_ROUTES: tuple[tuple[str, str], ...]     # admitted: take a place at the model before the body is read
OPEN_WHILE_UNREADY: tuple[str, ...]           # path prefixes answered before the self-test passed
CAPABILITY: str                               # "core" | "code" | "inspection" | "showcase"
def register(app: "FastAPI", state: "ServiceState") -> None: ...
def on_ready(state: "ServiceState") -> None: ...        # optional
```

`MANIFEST.serve.endpoints` is the sorted `"METHOD /path"` list of the modules whose capability is enabled in this bundle (§2.4); it is the single source of the service's routes, and the bundle's tests assert the registered routes equal it (the framework's own `/openapi.json` and the implicit `HEAD` routes aside). The routes as shipped: `routes_meta` (`core`) — `GET /`, `GET /console`, `GET /health`, `GET /v1/code`, `GET /v1/examples`, `GET /v1/info`, `GET /v1/schema`, open while unready `/health`, `/`, `/console`; `routes_predict` (`core`) — `POST /v1/predict`, `POST /predict` (the v2.2 alias, `serve.endpoint`), `POST /v1/predict/csv`; `routes_monitor` (`core`) — `POST /v1/monitor`; `routes_inspect` (`inspection`) — `GET /v1/network`, `GET /v1/network/tensor/{tensor_id}`, `POST /v1/explain` (§7.7); `routes_showcase` (`showcase`) — `GET /`, `GET /console`, `GET /showcase/{path:path}`, `GET /v1/story`, `GET /report.pdf`, `GET /v1/showcase` (§7.6), which takes over `GET /` and `GET /console` from `routes_meta` only through the service's page hook, and only for a verified showcase. `routes_meta` serves `/health`, `/v1/info`, `/v1/schema`, `/v1/examples` and the `GET /` and `GET /console` fallbacks; the service status (`ServiceStatus`, in `serve/service.py`) carries `inspection` and `showcase`.

**`/v1/code` stays in the core service** (`routes_meta.py`, capability `code`) as `vega/code-view@2` — the code shown is the verified code that runs:

```json
{ "schema": "vega/code-view@2", "verified": true, "language": "python",
  "files": [ { "path": "<pkg>/model/network.py", "role": "Model", "kind": "adapter",
               "digest": "sha256:…", "lines": 212, "text": "…" } ] }
```

`role` is one of `Model`, `FeatureTransformer`, `Predictor`, `ModelStore`, `Monitor`, `Inspection`, `support`, `composition_root`, `http_entry`, `ports`, `domain`; `kind` is `adapter`, `support` or `entrypoint`. No English `about` field is sent: the page renders `code.about.<role>` from its own strings.

### 7.3 Answers per reading

The HTTP answer is encoded generically from `MANIFEST.output.field_kinds`: each field's kind names the JSON key it lands under in a `RowPrediction`, and `serve/` contains no per-task branch. Every `RowPrediction` also carries `warnings`.

| field kind | JSON key | JSON shape | shown |
|---|---|---|---|
| `class` | `label` | string | always |
| `flag` | `labels` | the label names whose flag is 1 | always |
| `alarm` | `anomalous` | boolean | always |
| `probability` | `probabilities` | `{of: number}` | always |
| `raw` | `logits` | `{of: number}` (binary: the positive class) | `?include=logits` |
| `value` | `value` | number | always |
| `quantile` | `quantiles` | `{"<q>": number}` | always |
| `horizon` | `values` | `{"h<h>": number}`, or `{"h<h>": {"<q>": number}}` with quantiles | always |
| `score` | `score` | number | always |
| `row_score` | `reconstruction_error` | number | always |
| `cumulative` | `cumulative` | `{of: number}` | always |
| `recon` | `reconstruction` | `{of: number}` | `?include=reconstruction` |
| `embedding` | `embedding` | numbers in coordinate order | `?include=embedding` |
| `decision` | — (`label` carries it) | — | CSV only |
| `group` | `graph_id` | string | always (graph level) |
| `answered` | `answered` | boolean, default true | always |
| `warnings` | `warnings` | list of strings | always |

So the answer keys per reading are:

| reading | keys |
|---|---|
| `binary`, `multiclass` | `label`, `probabilities`, and `logits` on `?include=logits` |
| `multilabel` | `labels`, `probabilities`, and `logits` on include |
| `ordinal` | `label`, `probabilities`, `cumulative`, and `logits` on include |
| `regression` | `value` |
| `quantile` | `value`, `quantiles` |
| `forecast` | `values` (`horizon` finite entries) |
| `reconstruction` | `reconstruction_error`, and `reconstruction` on `?include=reconstruction` |
| `anomaly-reconstruction` | `score`, `anomalous`, `label` when labelled, and `reconstruction` on include |
| `anomaly-svdd` | `score`, `anomalous`, `label` when labelled, and `embedding` on `?include=embedding` |

The CSV answer's columns are `MANIFEST.output.fields`. The thresholds a caller needs to read an answer are in `/v1/schema.output` (`threshold`, `threshold_scale`, `threshold_per_label`). A window row without enough history answers `answered: false` with its warning and a 200 — never a 422; 422 remains for `/v1/explain` and for a request the row contract refuses. `p_<positive> ∈ [0, 1]` and the binary decision is `p_<positive> ≥ threshold`; an anomaly answer's `anomalous` is `score ≥ threshold`.

### 7.4 Examples — `vega/examples@2`

`GET /v1/examples` answers `vega/examples@2`, assembled once at start-up from the verified `examples/*.json` and `examples/rows.csv`; `references/schemas/examples-2.schema.json` is its JSON Schema (draft 2020-12), and `examples/demo.json` and `examples/presets.json` validate against its `#/$defs/demo` and `#/$defs/presets_file`:

```json
{ "schema": "vega/examples@2",
  "test": { "source": "test", "rows": [ … ], "history": [ … ] | null },
  "demo": { "source": "train", "schema": "vega/demo@2",
            "strata": [ { "id": "class-0", "kind": "class", "name": "…", "n": 20, "range": null } ],
            "items":  [ { "stratum": "class-0", "rows": [ … ], "history": [ … ] | null, "truth": … } ],
            "rows": [ … ], "labels": [ … ] },
  "presets": [ { "id": "typical-class-0", "kind": "typical_correct", "group": "typical",
                 "stratum": "class-0", "expected": { "kind": "class", "value": "…" },
                 "facts": { "right": 19, "of": 20 },
                 "row": { … } | null, "rows": [ … ] | null, "history": [ … ] | null } ] }
```

- **Demo** (`vega/demo@2`): drawn from the **training part only**, never the test part (seed 7), `--demo-sample <n>` items per stratum (default 20; 0: none, and `demo` is null). For the row and graph shapes pack also writes `examples/demo.csv`, the demonstration rows as a caller would send them (a graph's rows whole), recorded with its digest in `MANIFEST.examples.demo.csv`; a window bundle has none (its items carry their own history). Strata per reading: one per class for the class readings; one per label plus `none` for multilabel (no label positive: its items' `truth` is `[]`, since a multilabel truth is a list of label names); five quantile `bin`s of the truth for the value readings (forecast: the first horizon's target), with their `range`; `all` and `flagged` for reconstruction; the classes for a labelled anomaly task, `typical` and `flagged` for an unlabelled one. A stratum's kind is one of `class`, `label`, `bin`, `none`, `typical`, `flagged`, `all`. Window items carry their `history`; graph items carry `rows` only. `demo.rows` and `demo.labels` are kept for the row class readings (the console page) only.
- **Presets:** `kind` is one of `typical_correct`, `typical_none_correct`, `typical_bin`, `typical_score`, `typical_sequence`, `edge_range`, `edge_infinity`, `edge_unseen`; `group` is `typical` or `edge`. `expected` is `{kind: class | labels | value | alarm, value, range?}` for a typical preset and null for an edge preset; a forecast's `value` is its whole horizon's truth, one number per step ahead (the bin is cut on the first). **No English ships in the payload:** a preset carries `facts` — `{right, of}`, `{bin: [lo, hi]}`, `{of}`, `{column, factor}`, `{columns}`, `{column, value}` — and the page renders `preset.<kind>.name` and `preset.<kind>.text` from its own strings table. A window preset carries `rows` and `history`; a graph preset carries `rows` only; a row preset carries `row`.
- The demonstration attributions are not the bundle's: `/vega-show` computes them through the bundle's inspector and writes them into the showcase.

### 7.5 The monitor per reading

`monitor-reference.json` is `vega/monitor-reference@2`. A monitor plan may use only the check kinds the bundle's reading admits; any other is refused at pack, `not admitted` (exit 2), and so is an unknown kind, field or class. References are measured on the training part (valid for the unseen rate, the recall and the output checks); rows answered `false` are dropped from a window before any reading, with a note. `MonitorRequest.labels` stays a permanent alias of `truth`.

| kind | needs | readings |
|---|---|---|
| `psi` | a column | every reading |
| `rate` | a column | every reading |
| `unseen_rate` | the recipe | every reading |
| `class_recall` | labels | `binary`, `multiclass`, `ordinal`, `anomaly-reconstruction`, `anomaly-svdd` |
| `output_psi` | predictions (the record's `score_field`) | `binary`, `regression`, `quantile`, `forecast`, `reconstruction`, `anomaly-reconstruction`, `anomaly-svdd` |
| `prediction_mix` | predictions | `binary`, `multiclass`, `ordinal` |
| `label_rate` | predictions | `multilabel` |
| `alert_rate` | predictions | `anomaly-reconstruction`, `anomaly-svdd` |
| `residual` | targets | `regression`, `quantile`, `forecast` |

An `output_psi` check on the `score_field` is added automatically wherever the reading has one.

### 7.6 The showcase slot

The bundle's service serves one demonstration page it did not build: `/vega-show` writes `<bundle>/showcase/` with its own manifest, `SHOWCASE.json` (`vega/showcase@1`, owned by `vega-show/references/show-contract.md` §5), and the service's `routes_showcase` module serves it. **The slot rule:** the showcase is pinned by its own manifest and never by the bundle's — `MANIFEST.files` never lists a `showcase/` path, the bundle's closed world and `verify()` are unchanged by it, and a refused showcase never makes the model unready.

- **Where.** `<ENV>_SHOWCASE` names the directory (`main --showcase DIR` sets it), else `<bundle>/showcase`. `MANIFEST.serve.showcase_slot` records the routes, the variable and the flag (§2.4).
- **Opens at start.** `routes_showcase.register` opens and verifies the slot synchronously, before the model's self-test, and its `OPEN_WHILE_UNREADY` is `("/", "/console", "/showcase/", "/v1/showcase")`, so the page can load its own modules and show "not ready".
- **Verified.** `SHOWCASE.json.schema` is `vega/showcase@1`; `bundle.manifest_digest` equals the sha256 of this bundle's `MANIFEST.json` bytes and `bundle.model_version` its `model_version`; every `files` digest holds; `served ⊆ files`; `entry` is a served `.html`.
- **Closed world.** Only `served` files are served, from memory, read once at start: `ETag` is the file's digest (304 on `If-None-Match`), `Cache-Control: no-cache`, `X-Content-Type-Options: nosniff`, and HTML carries the page's `Content-Security-Policy` (no external asset). `.md` is served as `text/markdown; charset=utf-8`. The slot refuses a showcase that holds a symlink, a path outside the directory, more than 64 MiB in total, or any file with a servable extension that is not in `files` and not under `.work/`, `.smoke/` or `docs/`. A refused showcase is `verified: false` with its reason, and `GET /` falls back to the console page.
- **Routes.** `GET /` serves the verified showcase entry, else the console page; `GET /console` always serves the console page (the service's own generic page, rendering any `RowPrediction` as a key/value table); `GET /showcase/{path}` a served file, else 404; `GET /v1/story` the showcase's story; `GET /report.pdf` its report, when linked; `GET /v1/showcase` and `/health.showcase` return the same status object, `{"present", "verified", "reason", "digest": "sha256:<SHOWCASE.json bytes>", "entry", "template": {"version", "manifest_digest"}, "report_status", "created_at", "files", "unlisted"}`.
- **Stale after a re-emit.** When `SHOWCASE.json.bundle.manifest_digest` equals some `MANIFEST.reemits[].previous_manifest_digest`, the showcase is stale: the slot refuses it with the reason `"the bundle was re-emitted after this showcase; re-run /vega-show"`, and `/vega` proposes `show`, not `pack`.
- **In the image.** `.dockerignore` keeps `showcase/` and excludes `showcase.prev/`, `showcase.building/`, `showcase/.smoke/` and `showcase/.work/`.

### 7.7 Inspection

Unless `--no-inspect`, the `package` templates render `<package>/<serving module>/inspection/` and `routes_inspect` serves `GET /v1/network` (`vega/network-view@2`) and `POST /v1/explain` (`vega/explanation@2`), under `vega-forge/references/inspect-contract.md`. Weights exposure defaults to `full`; `--inspect-weights summary` or `<ENV>_INSPECT_WEIGHTS` restricts it, and the choice is recorded as a stance. After the round trip passes, pack runs the inspector's self-test on an example; a failure is `ERROR: inspection: <why>` — a template defect, fixed in the backend's inspection templates and never in the bundle — and a pass records `MANIFEST.serve.inspection` (§2.4) with the network digest in both modes. When inspection is off, the inspection routes answer 404 and the page shows its not-available state.

- **The self-test and the pin.** Pack opens a `NetworkInspector` over the round-tripped Predictor on `examples/rows.csv`, at the tolerance `MANIFEST.roundtrip` carries, and requires it ready (`ERROR: inspection: <why>`, exit 3 otherwise — a defect of the backend's inspection templates, fixed there; a one-class network whose checkpoint lacks its centre names the trainer instead). Ready, it pins the network digest of both weights modes in `MANIFEST.serve.inspection.network_digest`, and the inspector checks that pin whenever it opens again — at the service's start-up and in `predict.load_inspector` — refusing a network that is not the one packed. The record is written in every mode that carries the Predictor's module (a batch bundle included: `load_inspector` is the library path `/vega-show` uses without a service).
- **`--no-inspect`** ships no `inspection/` package at all: `MANIFEST.serve.inspection.enabled` is false, the Predictor's `inspector()` refuses, the inspection routes are not rendered, and the bundle's inspection tests skip with the reason `packed with --no-inspect`. Only `--no-inspect` and `--inspect-weights summary` are recorded in `MANIFEST.stances`; the default, `full`, is the record's `weights`, not a stance.
- **The routes** (`routes_inspect`, capability `inspection`). They open on the service's start-up, after the self-test passed (503 before it): the Predictor's own inspector on the example rows, its status (`enabled`, `ready`, `why`, `weights`, `network_digest`, `pinned`, …) reported as `/health.inspection` and in `/v1/info`. An inspector that does not open never costs the model its readiness — the routes then answer 404 naming why. `GET /v1/network?weights=full|summary` (no parameter: the published mode) answers bytes built once per mode; `GET /v1/network/tensor/{tensor_id}` one tensor from the live weights; `POST /v1/explain` is admitted at the model before its body is read, holds its rows to the `/v1/predict` row model, and its `prediction` equals the `/v1/predict` answer of the same rows. `MANIFEST.serve.inspection.enabled: false` or `<ENV>_INSPECT=off` answers all three 404 before any body is validated; `summary` (by the record or `<ENV>_INSPECT_WEIGHTS=summary`) withholds every tensor, and `weights=full` and the tensor route answer 404. Refusals: 422 for the request and the query — a row the row model refuses answers the same problem body `/v1/predict` gives (naming the column), a query the explain rules refuse answers inspect-contract's refusal body — a window short of history says `a window needs <length> rows ending at \`at\``); 404 when inspection is off or unavailable and for an unknown or withheld tensor; 500, with no internals, for an explanation that does not reproduce the served answer or an attribution that cannot be given. A graph row whose keys match no reference node is answered 200 with the warning `no neighbour in the reference graph — answered from the row's own features`. The payloads are `vega-forge/references/inspect-contract.md`'s.

### 7.8 `--re-emit-serving`

`pack.py <the same inputs as the original pack> --re-emit-serving [--reason "<text>"]` re-renders only the serving adapters of an existing bundle, and proves it did. It needs `bundle_dir/<slug>-<run>/MANIFEST.json` (else `ERROR: no bundle to re-emit`, exit 2) and a bundle that still verifies against its manifest (else `ERROR: the bundle is not the one its MANIFEST pins; re-pack instead`, exit 2). It then runs the whole pack into a staging directory that keeps the bundle's own name, `<bundle-dir>/.reemit/<slug>-<run>/` — the same provenance, transformer, twin check, round trip, examples, monitor, inspection self-test and gate — and compares the two bundles: the pinned files and the manifests. One re-emit of a bundle runs at a time, because the staging directory is the bundle's own. `--reason` without `--re-emit-serving` is a usage error (exit 2). The re-emit takes the inputs of the pack that built the bundle: when a manifest key that echoes an input moved (`blueprint.run` ← `--pipeline`, `chain.model` ← `--model`, `include` ← `--include`), the refusal names both values.

- **May change:** the outputs of the serving templates, named by the same patterns as `serving_templates` (`package/*.py`, `package/inspection/*.py`, `serve/*.py`, `serve/static/index.html`, `bundle/*`, `tests/*.py`) at the destinations where pack renders them (the Predictor's and the Monitor's adapter files wherever the map puts them; each `bundle/<name>` as `<name>` at the root), the export files (exported again from the same weights and re-checked), and in the manifest `created_at`, `reemits`, `blueprint.conformance`, `serve`, `roles`, `roundtrip`, `exports` and the `files` digests of those outputs. The other listings of bundle files — `entrypoints` and the package's `blueprint-map.json` — may differ only in the entries that name one of those outputs, so a template the backend adds is re-emitted like one it changed. `requirements.txt`, `ports.py` and the package's `__init__.py` stay byte-identical.
- **Never changes:** `weights.*`, `netspec.json`, `recipe.json`, `fitted.json`, `schema.json`, `monitor-reference.json`, `examples/*`, `graph/*`, `records/*`, and any `<package>/` file that is not one of those template outputs (the Predictor's and the Monitor's adapter files may sit in any module the map names; every other package file — the network, the store, the data adapter, wherever the blueprint put them — is pinned) — what the evaluation pinned is not the serving templates' to change.

Anything outside *may change* that differs refuses the re-emit: `ERROR: re-emit would change <files>; what the evaluation pinned is not the serving templates' to change — re-pack deliberately` (exit 3); the staging directory is deleted and the bundle stays untouched. Otherwise the stage prints `GATE: replacing <root> with the re-emitted serving adapters (<n> file(s): …)` (attended it asks; unattended the flag is the consent, and the gate line is recorded), carries over the files other stages wrote beside the bundle (the model card, the notebook, the layer's authoring file, a showcase — moved byte for byte, never written or re-pinned by pack; the showcase is stale from then on), swaps the staging directory in (`rename(root → .prev)`, `rename(staging → root)`, remove `.prev`; the old bundle is put back if the second rename fails), and appends to `MANIFEST.reemits` (§2.5). The layer, the card, the notebook and the brief are then republished, because the manifest digest changed; a showcase built on the previous manifest is stale (§7.6).

### 7.9 Stream

A `stream` bundle (a window shape: the forge compiles `stream` only for a windowed sample, and never for a bidirectional family) serves through `serve/consumer.py` — `python -m serve.consumer [--bundle DIR] [--input rows.jsonl] [--output answers.jsonl] [--batch-rows 256] [--history earlier.csv] [--include logits] [--monitor moved|all|off]` — and renders `serve/{__init__, consumer, contract, answers, problems, rows, tables}.py`, no `app.py` and no HTTP route (`serve.endpoints: []`; the `pyproject.toml` serve command, if any, is `serve.consumer:main`). Before a row is read every pinned file must hash to its digest and the examples reproduce (`check_examples`). Each batch of JSON lines goes through the row contract — a row that breaks it is not answered, and its batch's problem line (422) comes first, naming every offending column with the rows' stream positions — then `predictor.predict(rows, history=buffer)` with, per series (`MANIFEST.sample.series_by`), the last `history_rows` accepted rows: windows complete across batches, so each answer is the one a single request holding the whole stream gets, and a cold start answers the first `length − 1` rows of a series `answered: false` (`--history` seeds the buffer). The sink receives one JSON line per batch — the answer envelope with `batch` and `positions`, plus the monitor's readings when a reference exists — before the buffer is extended. A refused row is the stream's equivalent of a refused HTTP request: it is reported, never dropped silently — its batch's problem line names it with its stream position, and it is absent from the history buffer. So the equivalence the consumer holds is with a single request holding the stream's **accepted** rows: the rows after a refused one are answered over their series without it, exactly as such a request would answer them, and each answer the refused row's absence reaches — the next `history_rows` rows of its series after it (of every series, when the refused line names none) — carries the warning *a refused row earlier in this series is missing from this answer's window* (`serve/gaps.py`, rendered with the consumer), so no window is silently shorter than the stream's — a caller that needs every window over the full series reads the problem line's positions and resends the corrected row before the rows that follow it. Exit 0 when the source was read to its end, 2 on a refusal, 3 when the examples differ.

### 7.10 The serving matrix

What proves that every reading and every sample shape serves is `scripts/tests/serving_matrix.py` (`vega/serving-matrix@1`): 17 cells, M01–M17 — `binary`, `multiclass`, `multilabel`, `regression`, `quantile`, `ordinal`, `reconstruction`, `anomaly-reconstruction` (labelled), `anomaly-svdd` (unlabelled) on rows; sequence classification over a multiclass, a binary and a multilabel base (M17), sequence regression and a forecast with H = 3 on windows; binary and regression at node level (M15 on `knn` edges) and multiclass at graph level — each over the families the table lists (the release gate runs all 27 runs over the 21 families; `--quick` one family per cell). Each run carries the backend coverage matrix's raw table through the **real** chain: the real `shape.py` (a `lag` step of an exogenous column in every window cell, the `graph_edges` step in every graph cell), `compile_spec`, the real emitter with its smoke pass, C0–C10 on the package, a seeded 3-epoch fit through the package's own `Trainer`, the campaign `/vega-train` leaves, the **real** `vega-eval/scripts/evaluate.py` under its seal, and the real `pack.py --serve --unattended --demo-sample 5 --monitor-plan <plan>` — the round trip `pass`, the reading, shape and level the cell names, every `[project.scripts]` target of `pyproject.toml` naming a shipped module and a callable it defines; then `predict.py --check` and `pytest <bundle>/tests` in an emptied environment, every test passing or skipping only with a reason the cell allows. M13 is also packed against a `stream` blueprint: `serve/consumer.py` is the adapter, `serve/app.py` and any command pointing at it are absent, and the test part streamed in batches shorter than a window answers row for row as one batch holding the whole stream does. Green is `summary.failed == []`. A reading × shape combination that no cell names (quantile on windows, multiclass at node level) packs, round-trips and tests like any other bundle; what it lacks is the matrix's sweep over the families, and pack does not refuse it for that.

```json
{ "schema": "vega/bundle-layer@1",
  "manifest": { "...": "MANIFEST.json verbatim" }, "input_schema": { "...": "schema.json verbatim" },
  "roundtrip": { "status": "pass", "rows": 120, "tolerance": { "rule": "1e-6 * max(1, max|score|)", "value": 1e-6, "precision": "fp32" }, "max_abs_diff": 0.0, "log": "…" },
  "exports": [ "…" ], "serve": { "...": "…" }, "code_findings": [ "…as in netspec-contract.md §4…" ],
  "model_card": { "path": "bundle/orders-late-H1-14/model-card.html", "digest": "sha256:…", "bytes": 412000 },
  "notebook": { "path": "…/predict.ipynb", "executed": true, "digest": "sha256:…" },
```

Required: `schema`, `manifest` (with `blueprint.conformance.mechanical: pass` over C0–C14 — the mechanical half, which refuses on any finding), `conformance` (per tool — `architect`, `improve` — the judgement vega-forge's `audit_quorum` makes of the audits, `code-contract.md` §5 *Reproduced, or recorded*: one first audit with no structural or divergence finding, or the first and two fresh audits of the same bundle; `structural` and `divergence` counting the findings two of the three audits confirm; every audit in `audits[]` (each with its `run_id`, no two alike), every blocking-class finding's matching in `matching[]`, no `pending` and no `invalid`; and `advisory` — `code-contract.md` §5 *Advisory*: `mode`, `outcome` (`clear`, `warn` unattended, `accepted` attended), every confirmed finding as an open item for `/architect` and `/improve` with its `WARN:` in `markers` and its `open_item` in `code_findings` — or, for a tool that did not run, no record and that tool's absence in `markers`, its name as a word), `forks` (optional; attended, the user's answer to each confirmed finding's `FORK:` — `{"gate": "<tool>", "findings": ["<audit>:<id>", …], "asked", "answer": "<fix now | accept and record | stop> — …"}`, only *accept and record* publishing), `code_findings` (may be empty; each finding tagged with its `tool` and `audit` and, when blocking-class, its `quorum` (`reported_by`, `confirmed`), spliced from every `--architect-run` and `--improve-run`, each flag once per audit, the first first), `input_schema`, `roundtrip` with `status: pass`, `model_card`, `usage` (spliced from `MANIFEST.usage`, which `pack.py` writes), `notebook` (written by the apply script from `--notebook <path>`, notebook-contract.md §3), `readings.abstract`, `readings.intended_use`. The authoring file (`bundle-layer.json`) carries `from_bundle`, consumed and not stored, naming the bundle directory whose manifest, schema, round-trip and parity results, serve record, card record and the `conformance` records and `code_findings` it splices in from the audits named by `--architect-run` and `--improve-run` (the shape netspec-contract §4 gives them, with the skill's `next` lines merged by tool, audit and id; an authored `conformance` is never read; `--unattended` when the stage runs unattended). `scripts/apply_bundle_layer.py` validates this, refuses a layer whose round trip did not pass, whose mechanical conformance is not `pass`, whose judgement is pending, invalid (run ids included) or malformed (an advisory block that does not carry every confirmed finding), whose confirmed finding has — attended — no recorded answer or the answer *fix now* or *stop*, or whose notebook is missing (a confirmed finding refuses no unattended layer: it is advisory), injects the shipped `assets/bundle-render.js` + `assets/bundle-layer.css` through `domain-forge/scripts/apply_layer.py`, and adds a `<noscript>` fallback (the manifest summary, the usage lines, the intended use).

The render mounts one tab, `data-layer="bundle"`, labelled **Bundle**: the manifest summary (run, verdict line, exposures, digests folded), the input schema table, the round-trip and parity results, the usage snippets, a link to the model card, the intended-use prose, and the audits' findings with each tool's judgement and every confirmed finding's open item. It reads only `layer-bundle-data`, idempotent, empty state when missing, ≤ 40 KB of JS, `window.__bundle = { manifest(), version }` for tests.
