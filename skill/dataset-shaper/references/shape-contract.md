# dataset-shaper contract — the recipe, the outputs, the `shape` layer

`/dataset-shaper` turns *decisions already taken* into a new dataset. The decisions live in the layers of the input HTML — `geometry` (from `/dataset-forge`: typing, basis, derivations, cycle orientations, partition and leakage set) and `analysis` (from `/data-lens`: findings and their transformation candidates, user stances) — and in what the user says during the run. The skill compiles them into a **recipe**, executes the recipe with a script, verifies the result, and records everything as one additive `shape` layer. The recipe is the truth: the script does exactly what it says, the reproduction script does the same without the skill, and the layer shows it.

## 1. The recipe (`recipe.json`)

```json
{
  "schema": "dataset-shaper/recipe@1",
  "input": { "path": "orders.csv", "digest": "sha256:<file digest>", "rows": 600, "columns": 15,
             "model": "orders.domain.analysis.html", "model_digest": "sha256:<canonical Turtle digest>",
             "layers_read": ["geometry", "analysis"] },
  "seed": 7,
  "goal": "train-ready | clean | basis-only | spatial-features | custom",
  "target": "late | null",
  "steps": [
    {
      "id": "S1", "op": "retype", "columns": ["zip"], "params": { "to": "nominal" },
      "source": "geometry:typing/zip",
      "rationale": "postal code parsed as integer; categorical by meaning",
      "alternatives": [],
      "consequences": { "rows": "none", "columns": "none", "downstream": "one-hot or target encoding later, not scaling" },
      "reversible": true
    },
    {
      "id": "S4", "op": "drop_derived", "columns": ["total", "subtotal"],
      "params": { "orientation": { "price-qty-total": "total-derived" } },
      "source": "geometry:cycles/price-qty-total",
      "rationale": "keep the basis; total and subtotal are rule heads under the chosen orientation",
      "alternatives": [ { "params": { "orientation": { "price-qty-total": "unit-price-derived" } }, "when": "if unit_price is the unobservable quantity at prediction time" } ],
      "consequences": { "rows": "none", "columns": "−2", "downstream": "a linear model no longer sees an exactly collinear column" },
      "reversible": false
    },
    {
      "id": "S6", "op": "impute", "columns": ["delivered_days"],
      "params": { "strategy": "group-median", "by": ["zip"], "indicator": true, "fit_on": "train" },
      "source": "analysis:F1/T1",
      "rationale": "missing not at random across zip (F1)",
      "alternatives": [ { "params": { "strategy": "median" }, "when": "if the zip dependence is judged spurious" } ],
      "consequences": { "rows": "none", "columns": "+1 (delivered_days_missing)", "downstream": "the indicator lets a model use the missingness itself" },
      "reversible": false
    },
    {
      "id": "S9", "op": "split", "columns": [], "params": { "kind": "stratified", "by": "late", "test": 0.2, "valid": 0.1 },
      "source": "shaper:default",
      "rationale": "no time column; stratify on the label so rare positives survive in every split",
      "alternatives": [ { "params": { "kind": "group", "by": "customer_id" }, "when": "if rows of one customer must not straddle splits" } ],
      "consequences": { "rows": "600 → 420 / 60 / 120", "columns": "none", "downstream": "every fitted step after this one is fitted on train only" },
      "reversible": true
    }
  ],
  "outputs": { "dir": "shaped/", "format": "parquet | csv", "files": ["orders.train.parquet", "orders.valid.parquet", "orders.test.parquet"],
               "recipe": "shaped/recipe.json", "manifest": "shaped/manifest.json", "lineage": "shaped/lineage.json", "reproduce": "shaped/reproduce_orders.py" }
}
```

**Sources** are the provenance tags of every step and the rule that makes the recipe honest: `geometry:<path>` (a typing entry, a derivation, a cycle orientation, the partition — paths use the geometry layer's own key names: `geometry:typing/zip`, `geometry:derivations/total`, `geometry:cycles/price-qty-total`, `geometry:partitions/late`), `analysis:F<n>/T<m>` or `analysis:turn<N>/T<m>` (a transformation candidate, from a finding or a dialogue turn) or `analysis:<path>` (an analysis-layer element by its path — `analysis:context.time`, `analysis:F<n>` — the form the step catalog's usual sources take; the executor's grammar admits both, and the existence check below is what makes either honest), `user:<turn or stance>` (something the user said in this run, or `user:stance/ST<n>` for a recorded analysis stance), `shaper:default` (a step the skill added on its own because the goal requires it — always with a `rationale` and at least one alternative — the recipe checker warns, naming the step, on one that carries none). A step with no `source` is refused by the executor. A step whose `source` names a layer path that does not exist in the input HTML is refused too, and so is a `custom` step whose source is not `user:` (nothing else can justify code the catalog does not define). A `geometry:` choice was settled by the geometry layer (its default orientation, its partition, its leakage set) and is shown with its alternatives, not asked again; the forks are the `shaper:default` and `analysis:` choices memory has not settled. A `user:stance/…` source cites only a stance a person decided: a default applied unattended is recorded as `default applied (unattended)` and never becomes a stance, so it is asked again on the next attended run.

**The label is not a droppable column.** The executor pre-scans the recipe for `select_partition`, so the target is known before the first step runs: a step that would remove it — `drop_derived` on a rule head that happens to be the label, `drop_constant` on a rare one — keeps it and reports that it did. Only a `user:` step that *names* the label in its `columns` may remove it.

**Order** is semantic, and the executor enforces the phases: (1) typing and structure — `retype`, `drop_identity`, `drop_constant`, `dedupe`, `parse_datetime`, `parse_geometry`; (2) geometry — `orient_cycle`, `drop_derived`, `select_partition`, `drop_leakage`, `keep_columns`; (3) split — `split` (at most one; after this every *fitted* step is fitted on the train part and applied to all parts); (4) values — `impute`, `clip`, `winsorize`, `transform`, `bin`, `datetime_expand`, `lag`, `spatial_*`; (5) representation — `encode`, `scale`, `project`; (6) selection — `select_features`; (7) graph — `graph_edges` (last, so a kNN reference is built in the fitted space the network sees and the train-only index comes after the split by construction). A `custom` step declares its `phase` and the executor places it there; it runs once per split part on that part's frame alone, so it cannot fit across parts, and the layer marks it *unverified*; in the two pre-split phases a `custom` step is structural (a retyping, a parse, a row filter) and may compute nothing a later part would inherit — the recipe checker refuses a pre-split `custom` step that declares `fitted: true`, and the executor's row-locality probe is the check on the rest (below). The executor rejects a recipe whose steps are out of phase (an `encode` before `split` when a split exists is the classic leakage) and says which step and why.

**Leakage the phase order cannot see.** Four rules hold where a phase order says nothing, each refused by the recipe checker (`shape.py`, `ERROR:` and exit 2, before any data moves), again by the executor where the step runs (exit 3), and by `verify_shape.py` on a recipe or manifest published with it (§3):
- *An `impute` or a `lag` grouped by the label* (an impute's `params.by`, a lag's `params.group_by`, naming the partition's label, as a list or one name) is refused whatever its source, a `user:` step included, and the refusal names the step and the label: a row's filled value would be the statistic of the rows sharing its label, and its lagged value would be read from the previous row sharing its label, so the label reaches its features — an evaluation the served answer cannot reproduce, since a query has no label (nor a label to group its history by). Group an impute by a feature, or impute without a group (an `indicator` keeps a label-dependent missingness visible); group a lag by the series key, or lag without a group. The lag *of* the label, grouped by the series key, is not this rule: it reads the label from the history (§2).
- *A group split's key is never a feature* (F33). A `split kind: group` puts each group whole into one part, so every valid and test row carries a group the fit never saw: encoded, the key would be information in train alone and the encoder's reserved unseen value everywhere else — the network learns from it and the evaluation cannot score it. The executor drops the key at the split (the split's manifest record carries `key: {column, fate: "dropped", why}`, `lineage.json.removed` names the split, `output_schema` has no entry for it), the reproduction script drops it in the same block, and the transform-only module, which skips the split, still runs the split's key-drop lines, so a served row loses it too and need not carry it. The one exception is the graph key: when a `graph_edges` step names the split's key as its `graph_id` (level graph), it stays, with `role: key` and never `feature` (`key.fate: "graph key"`). A step after the split that reads the key — an `encode`, a `scale` or `bin` naming it, an `impute` or a `lag` grouped by it, any step whose `columns` or grouping parameters name it, `graph_edges` excepted — is refused whatever its source, naming the step and the key: it would make the key a feature again or read a column that is gone. Split by a group, then encode the other columns.
- *`select_features kind: importance` in a recipe that splits* (the default `kind`, so a step that names none) is refused: the analysis layer's permutation importance was measured before the split, over rows that are now the test part, so a selection by it has seen the test labels. After a split, select by `variance` (measured on the train part) or name the columns (`explicit`); without a split there is no test part for it to have seen.
- *A pre-split `custom` step must be row-local.* Before the split there is one frame, the future test rows in it, and reading code cannot decide what it computes — so the executor runs it: on the whole frame, then on four slices (the even rows, the odd rows, the first half, the second half), and refuses it (naming the step, the slice and the first difference) unless each slice's result is exactly the whole's rows for that slice — same index, same columns, same values, a missing value equal to a missing value. A mean, a rank, a frequency, a dedupe across rows or a random sample gives a slice another answer and is refused; a retyping, a parse or a filter on the row's own values passes. It must also keep each row's index, the raw-file position the split records (a step that renumbers, adds or repeats rows is refused). The probe is a test, not a proof — a cross-row computation that happens to agree on all four slices passes it; what covers the rest is the source rule (a `custom` step is `user:` only, so a pre-split one is the user's own claim that it is row-local, quoted in the recipe) and the layer's *unverified* mark, which the summary repeats — and the manifest records that it ran (`parameters_fitted.row_local_probe: {probe: "row-local", passed: true, rows, slices}`); the verifier refuses a pre-split `custom` step without that record. After the split a `custom` step runs per part and is not probed.

**Edges are a claim, not a default.** A `graph_edges` step is after `split` — a split must exist, since the parts are what its edges record — and its source is `analysis:` or `user:`; the executor refuses one with any other source (`shaper:default`, `geometry:` …), one before the split, or one in a recipe without a split, beside its other structural rules (no basis member dropped without a `user:` step, no fitted step before `split`, no step without a source). A recipe carries at most one `graph_edges` step, and one with a `graph_id` needs a `group` split by that column (a graph whose rows straddle parts would be trained on and tested on at once); a `key_pair` cap (`max_clique`, `max_degree`) needs a `graph_id` too, because at level node it ranks candidates by raw position, which a served row does not carry, so `edges_for` could not reproduce the capped edges the evaluation sees; the step's parameters are checked with the recipe (`step-catalog.md` phase 7) and the columns they name when the step runs. It changes neither rows nor columns: its output is the `edges` part (§2).

Every step carries `consequences` with three entries (`rows`, `columns`, `downstream`), each a concrete effect or "none"; `alternatives` are the ones actually weighed (empty when forced, and `rationale` says why); `reversible` says whether the step can be undone from the output alone (a retype or a split can; a drop, an imputation or a projection cannot — the input file is the reversal, as in every chain skill).

## 2. The executor and its outputs (`scripts/shape.py`)

**Reading the input.** The executor reads the raw file with the non-finite tokens declared: `Infinity`, `-Infinity`, `inf`, `NaN` and their case variants are parsed as *missing*, never as real infinities (a bare `pd.read_csv` turns them into `±inf` that every `isna()`-based imputer misses), and the manifest records how many were found per column (`input.non_finite`); the reproduction script reads the same way. Row alignment between raw and shaped is always through `__split_raw__` (raw positions), never through `__split__` (post-phase-1 positions, which a `dedupe` moves); the verifier's semantic check uses the input's own agreement ratio as the baseline, not an absolute floor. `SOURCE_RE` admits column names with spaces and punctuation (`geometry:typing/Flow Duration`), quoting them when needed.

`python3 scripts/shape.py --recipe recipe.json --out-dir shaped/` reads the input dataset named in the recipe, checks the recipe (schema, phases, sources against the model's layers when `--model` is given, no step without a source, no label in the feature set of a `select_partition`, no leakage column surviving `drop_leakage`, no basis member dropped unless a `user:` step says so, no step contradicting an `analysis` stance — a `winsorize` or `clip` on a column a `genuine-outliers` stance names, an `impute` against a `missingness-mechanism` stance's strategy, any step on an `out-of-scope` column — unless a `user:` step overrides it and says so), executes the steps deterministically under `seed`, and writes:

- the dataset file(s) in the chosen format — one file, or one per split part;
- when a `graph_edges` step ran, the `edges` part — `<dataset-stem>.edges.parquet` / `.csv` beside the split parts, `outputs.files.edges` in the manifest with path, digest and rows like the other parts (schema and the manifest's `graph` block below); the reproduction script writes it too, so `--check` covers the graph as it covers the frame;
- `manifest.json` — `{ input digest, recipe_digest (sha256 of the recipe serialised as key-sorted compact JSON — `json.dumps(recipe, sort_keys=True)` — not of the file's bytes; a reader recomputes it the same way), steps[] {id, op, rows_before, rows_after, columns_added, columns_removed, fit_on, parameters_fitted (e.g. medians, encoders' categories and unseen_category_id, scaler statistics, PCA loadings)}, output_schema (column → dtype, role, origin step, and for ordinal-encoded columns encoded + unseen_category_id), outputs {dir, format, files (per part: path, digest, rows, columns), manifest, lineage, recipe, fitted, reproduce}, label, seed, library versions }`;
- `fitted.json` — every step's fitted parameters in one file, which the reproduction script reads rather than carrying inline, plus four `__dunder__` keys the generated programs need: `__split__` (the split's index sets, as positions in the frame the split saw), `__split_raw__` (the same sets as raw-file row positions), `__removed_rows__` (the raw positions a `dedupe` removed) and `__code__` (the lines emitted per step, which `--transform-only` re-emits);
- `reproduce_<slug>.py` — a standalone script (pandas + numpy + scikit-learn, optional geopandas/pyproj for spatial steps) that re-executes the recipe from the input path without this skill installed, one readable block per step, and asserts the output digests recorded in the manifest. It is a second implementation of the same recipe, which is what makes `--check` a test rather than a tautology;
- `lineage.json` — column → the steps that touched it, for the layer's lineage graph, and `removed_rows`, the raw positions a `dedupe` removed.

**The `edges` part** (`graph_edges`, phase 7) has the schema `src_pos: int, dst_pos: int, src_part: train | valid | test, dst_part: train | valid | test, weight: float | null` — one row per directed edge, ordered by `(src_pos, dst_pos)`, each directed pair once, both directions written when `symmetric` is true (the reverse carrying the edge's weight), `weight` null throughout when the step's `weight` is null. `src_pos` / `dst_pos` are **raw-file row positions**, the convention `fitted.json.__split_raw__` already uses (not `__split__`, which addresses the frame the split saw; the two differ exactly when a `dedupe` ran first): a position resolves to a row of the part `*_part` names through `__split_raw__[part]`, which the shaped parts preserve in order, and a position is stable across every step that removes rows. The manifest carries a `graph` block beside `steps[]`: `{ step, method, params, n_nodes: {train, valid, test}, n_edges, directed, symmetric, self_loops, weight, cross_part_edges: {"train-valid": n, "train-test": n, "valid-test": n}, within_part_edges: {train, valid, test}, isolated_nodes: {train, valid, test}, level: node | graph, graph_id: <col> | null, fitted: bool, edges_for: {columns, raw} | null, edges: "outputs.files.edges" }` (plus `capped_groups` for a capped clique) — `n_nodes` are the parts' row counts (every row is a node, joined or not), `n_edges`, the `cross_part_edges` (unordered part pairs) and the `within_part_edges` counts are rows of the part, `directed` is `not symmetric`, `level` is `graph` iff `graph_id` is set, `params.features` is what `"basis"` resolved to, `fitted` is true for `knn` and `spatial` at level node, and `edges_for` (level node) names the reference columns `edges_for` reads (`EDGES_FOR_COLUMNS`) and maps each `raw:<column>` to its input column — what `/vega-pack` writes into `graph/reference-nodes.parquet` beside `ref` and the shaped features, and lists as `graph.json.edges_for_columns`; the block is what `/vega-forge` reads as `shape:manifest/graph`. At level graph the graph key keeps `role: key` in `output_schema`: it reaches the shaped parts, because a graph-level network groups its nodes by it, and it is not a feature. In `fitted.json`, the step's entry carries `spec` — the step resolved against the frame (method, level, the input columns it reads at raw positions, the fitted columns, what `edges_for` needs of a reference: `reference.shaped`, the fitted columns under their own names, and `reference.raw`, each input column it reads under `raw:<column>` — a reference frame carries the shaped features too, and a raw key, weight or coordinate may share its name with one, a standardised `lat` beside the raw `lat`), the one literal the executor, the reproduction script and the transform-only module share — and, for a `knn` or `spatial` step at level node, the fitted reference: the train nodes' raw positions (`__split_raw__.train`, by reference), the **part and columns** of the matrix the index was built on (`part: "train"`, `columns: [...]` — the features `"basis"` resolved to, or the coordinate columns `parse_geometry` named; the matrix itself lives in the shaped train part, or is the train rows' raw coordinates projected as `spatial_reproject` recorded, and is not copied) with `matrix_digest`, the sha256 of that matrix in C order, rows in train-part order — as **float32** for `knn` (its fitted space: the dtype the network reads and `vega/graph-reference@1` stores, which every program rounds to before the float64 sums) and as float64 for `spatial` (raw coordinates, projected) — plus `n_reference`, `k` / `radius_m` / `metric` and `fit_on: "train"`. A `key_pair` step has no fitted reference: its keys are read from the input at the raw positions, and the manifest's `params.columns` names them. The three programs run one implementation of the step (`shape.py`'s `GRAPH_LIB`: the reproduction script carries it whole, the transform-only module the functions its entry point reaches, a private one without its docstring — the same code, which the emitter proves by parsing before it writes a line; each method binds its own functions to the role names the shared code calls, so a module carries nothing another method needs): distances are accumulated one feature at a time, so a pair's distance depends on those two rows only, and a tie goes to the candidate that comes first — in the train part for a fitted index, in the input's order within a graph at level graph.

`--transform-only --recipe recipe.json --fitted fitted.json --emit preprocess.py` emits a second standalone module, `preprocess.py`, exposing `transform(df_raw, history=None) -> df_shaped` (the keyword is always present; only a `lag` recipe reads it): the recipe applied in phase order to new rows with the parameters already fitted. It is not a second implementation of the recipe. `fitted.json.__code__` records, per step, the very lines the executor emitted into `reproduce_<slug>.py`; this mode **re-emits a filtered subset of them over a single part** (`parts = {"rows": df_raw}`), so the training program and the serving program are one program read two ways, and an op whose emitted line cannot serve a query unchanged is a defect in that op's emitter rather than something the transformer works around. The mode reads the recipe and the fitted file and nothing else — never the dataset, because it exists to shape rows that do not exist yet.

Two questions decide each op, and confusing them is silent: does the step shape the training *corpus* or the *row*? **Skipped** — `split` (a query is one part) and `dedupe` (deduplicating a query returns fewer predictions than rows given; duplicate rows are duplicate questions). **Recorded, not applied** — `select_partition`: it names the label, so the module carries `LABEL` and `PARTITION`, and filters no row (the caller supplies the rows of the partition; dropping any here would answer fewer questions than were asked, without saying so). **When the label leaves.** The executor keeps the label in every part to the end, so a step after `select_partition` that reads it — a `lag` of the target — reads it there; the module therefore keeps the label until the **last** such step has run and drops it right after (with none, where the partition is named) — dropped any earlier, the first of those steps would raise on a column the executor had. (An `impute` or a `lag` grouped by the label never reaches the module: the recipe checker and the executor refuse it, §1, *Leakage the phase order cannot see*.) A query row carries no target: a step that repairs the label in place runs on a placeholder, and a lagged label is read from the **history** rows (`HISTORY_COLUMNS` lists what a history must carry: the columns the query needs and the label when a lag reads it — a history without them is refused, naming the columns, never answered with missing lags). **Applied** — everything else: `retype`, `parse_datetime`, `parse_geometry`, `orient_cycle`, `datetime_expand`, `spatial_*`, `impute`, `clip`, `winsorize`, `transform`, `bin`, `encode`, `scale`, `project`, `custom` with the fitted parameters, and `drop_identity`, `drop_constant`, `drop_derived`, `drop_leakage`, `keep_columns`, `select_features` as **column selection by name** (the executor resolved the names when it ran; nothing is re-decided from these rows). `lag` is applied and needs the rows before the query: `transform` prepends `history`, takes the lags over the whole window and returns only the query rows (the executor reads the lags over each part in time order and **writes them back by row label**, so a part keeps the row order the split gave it — the order `__split_raw__` records, which every reader that aligns a part with its raw rows by position relies on; `verify_shape.py` checks each part's order against `__split_raw__` and fails a part that was re-sorted), and with `history=None` it raises naming the flag (`predict.py --history <file>`) rather than emitting NaN lags the network will score without complaint. A `custom` step is carried verbatim with a `WARN:` in the module's header (unverified, as in the layer). `spatial_features` is batch-independent: its neighbour features read the index fitted on the train part, which `fitted.json` carries (§2, *Fitted steps*), never the frame they are given — a one-row query reads what it would read inside any batch, and the twin check holds on every part. A required input column missing raises with its name, checked on the query before the history is prepended.

Encoding of an unseen category. Training data cannot contain every category, so every encoder records what an unseen value becomes as a *fitted parameter* rather than as a fallback in the code: `parameters_fitted.<column>.unseen_category_id = len(mapping)` for an ordinal one — the reserved id the executor maps unseen values to **in every part it writes** (train never contains one; valid and test may) and the id `/vega-forge` sizes the embedding from as `unseen_category_id + 1` — `unseen_value` (0.0, and the prior) for a frequency and a target one, and all-zero indicators for a one-hot one, which is a defined and honest state but still a row the model has no evidence about. All three are recorded **per row**: `last_unseen()` returns one list of column names per returned row, in the returned row order, and `predict.py` puts them in its `warnings` column. Both generated programs call the same emitted `_unseen(...)` line — the reproduction script counts them into a `WARN:`, the module keeps the rows.

`verify_shape.py --transform-only --recipe recipe.json --out-dir <dir> --module <preprocess.py> [--part test]` is the twin check, and the only test of `preprocess.py` that does not go through a network: it fetches the raw rows the shaped part came from (`fitted.json.__split_raw__`, whose indices are **raw-file row positions** — `__split__` addresses the frame the split saw, and the two differ exactly when a dedupe ran first, which `lineage.json.removed_rows` records), runs them through the module, and asserts equality with the part **on the feature columns, in their order**, byte for byte. A float column may miss that bar only by `1e-12 × max(1, |value|)`, the slack a reduction summed over a different number of rows can produce, and the check says which columns needed it and why; a category id, a bin number or an indicator gets no tolerance at all. A divergence names the column, the first row, both values and the step behind it from `lineage.json`. On a `lag` recipe the twin runs with an **empty** history window — the window the executor itself had, since `lag` is phase 4 and runs inside each part — and then reports separately how many rows the real preceding window moves: those are the rows a split boundary left without a predecessor, trained on as missing and served with a value, which is a reading about the recipe and not a verdict on the module. Exit 0 on agreement, 3 on a divergence. `/vega-pack` calls this emitter and this check; nothing else may re-implement the recipe. `--dry-run` writes the recipe, the manifest skeleton and the reproduction script, materializes nothing (large data, or a user who prefers to run it elsewhere) — and a dry run is not a run of the stage: with no shaped data there is nothing to verify, so it writes no layer, no brief and no summary, publishes nothing, and ends on the one marker `WARN: dry run — recipe compiled, nothing shaped; execute it to run the stage`; the stage runs when the recipe is executed. `--check` re-executes the reproduction script and compares digests (the determinism test the summary reports).

`graph_edges` is the one op the two questions above do not settle, because it shapes neither the corpus nor the row but the *relation* of a row to the corpus, so on a graph recipe the module carries two entry points beside `transform`, the inference-graph rule of the build plan (R-A3): **reference** nodes are the train and valid rows, **query** rows receive their edges from reference nodes only — never from another query row — so an answer never depends on the rows sent beside it.

- `edges_for(df_raw, reference, history=None) -> DataFrame[query_pos, ref_pos, weight]` (level node). `df_raw` is **raw** rows, as `transform` takes them; `query_pos` is a row's position in `df_raw`; `reference` is a frame with `pos` — an opaque node id, returned as `ref_pos` (`/vega-pack` passes the dense `ref` of `graph/reference-nodes.parquet`; no raw position ships) — and the columns `EDGES_FOR_COLUMNS` names: each input column it reads under **`raw:<column>`** (the key and weight columns for `key_pair`, the `parse_geometry` coordinates for `spatial`), as the input held it, and the fitted columns as shaped for `knn`, under their own names, float32 or float64. The namespace is what lets one frame carry both: `vega/graph-reference@1` holds every feature column as shaped, and a raw key, weight or coordinate may share its input name with one (`GRAPH["reference"]["raw"]` maps each `raw:<column>` back; the executor refuses a shaped column that already bears such a name). The rows returned are the query row's **attachments**: every (query, reference) pair the `edges` part would join in either direction — the query row's own edges (query → reference, in the step's direction) and the reference rows' edges into it (their own on a directed step, the reverses of the query's on a symmetric one) — each pair once, weighed by the query row's own edge when the pair runs both ways (a reference row's edge weighs the pair only when the query has none to it). A consumer orients every one reference → query, so the query receives messages and sends none; the evaluation's view attaches a query node by the same rule, which is what lets the bundle reproduce it. `key_pair` joins a row to the reference nodes whose key matches (a query without a key column raises with its name, as any missing input does); `knn` / `spatial` join it to its `k` nearest reference nodes — or those within `radius_m`, at most `max_degree` — among the nodes the index was fitted on, in the fitted space, computed on the query row *after* `transform` has taken it through the same phases: the reference lists the train nodes first, in the train part's order, as `vega/graph-reference@1` orders its `ref` ids (then the valid nodes), or holds them alone; its first `n_fit` rows are taken (fewer is refused) and their matrix is checked against the fitted `matrix_digest`, which the module carries in `GRAPH`. A float32 and a float64 copy of the shaped features give the same matrix (the space is float32); another order (a tie goes to the node that comes first), another scaling or valid nodes listed first are refused, never joined to other neighbours than the part records.
- `edges_within(df_raw, history=None) -> DataFrame[src_pos, dst_pos, weight]` (level graph). A query is whole graphs: the edges between rows sharing the `graph_id`, positions local to `df_raw`, never across two graphs, computed exactly as the shaper computed the part — caps and ties ranked by a row's place within its graph, so a caller sends each graph's rows in the order the input held them.

Each entry point raises on the other level, naming the one to call (a module carries the other level's as that refusal alone). `transform` itself leaves the frame alone: a new row is a node with no edges until `edges_for` / `edges_within` is called, and `predict.py` calls both. `verify_shape.py --transform-only` twin-checks them after `transform`: at level node it builds the reference as `/vega-pack` ships it (`vega/graph-reference@1`, whose layout `vega-pack/references/bundle-contract.md` §2.3 owns) from the parts before `--part` (train and valid for the test part, train for the valid part), and passes `nodes[["pos", *EDGES_FOR_COLUMNS]]` as the GraphAssembler does; runs `edges_for` on the part's raw rows, maps `query_pos` / `ref_pos` back to raw positions, and asserts equality with the part's attachments of those rows — its rows between them and the reference parts, in either direction, as (query, reference) pairs weighed as above; at level graph it runs `edges_within` and asserts equality with the part's rows inside that part; both byte for byte (`weight` with the float slack above). The part's query → query rows (test–test, a self loop) are reported as the count the served graph never carries by construction — a reading about the method, not a verdict on the module; for `knn` / `spatial` at level node they are zero by construction.

**The module's shape** (the code discipline of the package it ships in, `vega-forge/references/code-contract.md` §5: at most 30 statements per function). `transform` runs each applied step's lines — the executor's, unchanged — inside short functions of their own (`_step_<id>`, listed in `_STEPS` in recipe order), so a recipe of any length emits functions within the limit: the emitter only decides where one function ends and the next begins (a value read from a module constant is read again at the top of each function that uses it; any other name a line reads from an earlier line keeps the two in one function). **The limit of that split:** it moves whole statements, so a single emitted statement longer than 30 statements (a step whose one compound line nests that many) cannot be divided and lands in a function over the limit, which the bundle's conformance gate refuses (C11); no recipe the chain's lanes or the coverage matrix use comes near it, and the remedy is in the step's emitter, never a hand-edited module.

**Fitted steps** (`impute` with a statistic, `encode`, `scale`, `project`, `bin` with quantile or width edges (both read off the fit part; `custom` edges are given, not fitted), `winsorize` with quantiles; `transform` with `box-cox` or `yeo-johnson`, whose per-column λ is estimated on the fit part and recorded under `parameters_fitted`; `select_features kind: variance`, whose variances are the fit part's; `spatial_features` with a neighbour feature, whose index is fitted on the fit part; a spatial step whose metric projection falls back to the equirectangular one, whose centroid is the fit part's; `spatial_grid` with `aggregate`, whose per-cell statistics are the fit part's) record `fit_on: "train"` in the manifest when a split exists and are fitted on that part only; without a split they fit on the whole data and the manifest says `fit_on: "all"` so a later reader knows the estimate leaked nothing only because there was nothing to leak into. A step that fits nothing — a closed-form `transform` (`log1p`, `signed-log1p`, `log`, `sqrt`, `reciprocal`), an exact `pyproj` projection — records `fit_on: null`. `verify_shape.py` holds every step that fits, or records that it did, to the part it should have been fitted on (§3). **The neighbour index** (`spatial_features`, `n_neighbours_within` / `nearest_distance`): the fit part's rows with a finite location, projected into the step's metric space, kept as their distinct locations with the number of rows on each (`parameters_fitted.index: {points, counts, n_fit, fit_on}`, carried by `fitted.json` into the transform-only module); every part, and every served row, is answered from it — `n_within_<r>m` counts the indexed rows within `radius_m` of the row's location, `nearest_neighbour_m` is the distance to the nearest indexed location, both excluding the row's own location (distance 0: a train row does not count itself, and a served row standing on a train location reads what that train row reads). A valid or test row never counts another non-train row, and the value does not depend on the rows computed beside it. `encode` with `strategy: "target"` is refused outside a split (it needs out-of-fold fitting, which the executor performs only when `split` precedes it).

## 3. Verification (`scripts/verify_shape.py`)

Runs after execution and before the layer is written; the summary reports its markers.

- **Structural:** the label is absent from the feature columns; the leakage set is absent; every head of a kept derivation (semantic `confirmed`, not `kept: false`: a derivation the geometry layer rejected derives nothing, and its head is a basis member like any other, F44) whose orientation is active is absent unless a `user:` step kept it (then the manifest carries `kept_derived: [...]` and the layer says so); no basis member missing unless a `user:` step dropped it or a named step **replaced** it with its representation — an `encode` (its one-hot or embedding columns), a `project` (its components, `keep_named: false`), a `datetime_expand` (its parts) or a `bin` (its bins), each naming the member in its `columns`, so the manifest records which members were replaced and by what. Replacing is not dropping: the member's information is in the output in another form, and the source the step needs is the step's own (a `project` that replaces is `geometry:space` or `user:`); dropping — a column gone with nothing standing for it (`drop_identity`, `drop_constant`, `select_features`) — needs a `user:` step, and the recipe checker refuses one that drops a basis member without it.
- **Semantic, when parents were kept:** for every kept derivation whose body columns survive (a rejected one is recorded `empirical: not applicable` with why — there is no relation to recompute), recompute the rule empirically on the output (the formula, on retained rows) and report agreement (`empirical: confirmed | refuted`; a `refuted` is an `ERROR:` the apply script refuses to publish, whatever step broke it — a `transform` is extended to the cycle at compile time, and a `scale`, `clip` or `winsorize` on one kept member is caught here) — a transformation that silently broke a definitional relationship (a log on `qty` but not on `total`) is the defect this check exists for. When the model exposes the rule and a headless browser is present, also run the SWRL/Horn rule on a sample of the shaped rows through `domain-forge/scripts/run_query.py` and record `symbolic: confirmed | refuted | untested` as `/dataset-forge` does.
- **Distributional:** per-column PSI between input and output on the columns that were *not* meant to change (a `dedupe` or `clip` should not move a column it did not name); any drift above the threshold — PSI 0.25 (`--psi-threshold`), the conventional mark of a significant shift, recorded in `verification.json` beside each column's value — is a `WARN` naming the step suspected. PSI compares *distributions*: it sees a column that moved, and it cannot see a column that was merely reordered — row-level integrity is the semantic check's job, through the alignment described above, and the two checks are complementary rather than redundant.
- **Split hygiene:** no row in two parts; group and time constraints honoured; a group split's key in no part and absent from `output_schema` (or, the graph key at level graph, `role: key`), and no step after the split reading it (§1); for a label of at most 20 distinct values (a class code), each part's label rate — the mean of the code, a binary label's positive share — within an absolute 0.15 of the whole's (`--label-tolerance`), a part outside it a `WARN` naming the part and both rates; a label of more than 20 values — a regression target, or a class code with that many classes — has no single rate and is not read here (a stratified split places each class in every part the class is large enough to reach). The tolerance is absolute, so it is loose on a rare class: when the minority share is under 0.15 the skill passes a tighter `--label-tolerance` (half that share), so a part that lost its positives is a `WARN`. And the leakage the phase order cannot see (§1), read on what was published: no `impute` or `lag` grouped by the label; no `select_features kind: importance` in a recipe that splits; every step that fits (§2, *Fitted steps*), or records that it did, records `fit_on` — `"train"` after a split, `"all"` without one; every `custom` step before the split carries the executor's passed row-locality probe; a `spatial_features` neighbour index records the fit part, its counts add up to its `n_fit`, and it holds no more rows than that part. A failure here is `split: fail`, which the apply script refuses to publish.
- **Determinism:** `--check` re-runs the reproduction script; digests must match, and the script records the verdict (`determinism: pass | fail`) in `<out-dir>/verification.json`, the report `verify_shape.py --json` wrote — run it after the verifier; the layer's `verification.determinism` is that record, never typed (F45).
- **Spatial sanity, when spatial steps ran:** every geometry valid, CRS declared on output, no coordinate outside the CRS bounds.
- **Graph, when `graph_edges` ran:** structural — the file digests to the manifest's and has the schema above; every `src_pos` / `dst_pos` exists in `__split_raw__[*_part]`; no directed pair twice; the reverse row exists for every edge when `symmetric` is declared; no `src_pos == dst_pos` unless `self_loops` is; on a directed part, the out-degree within `max_degree` (and `k`); every edge stays inside one `graph_id` when set; for a fitted index (`knn`, `spatial` at level node) no edge joins two non-train nodes, and the fitted entry's `matrix_digest` is the train matrix's, recomputed from the shaped train part (knn, as float32) or the input's coordinates (spatial); and the `cross_part_edges`, `within_part_edges`, `n_edges` and `n_nodes` counts recomputed from the part equal the manifest's. Semantic, recomputed independently of the executor's code — for `key_pair`, the key equality holds on every edge, recomputed from the input at the raw positions (an edge whose keys differ is the defect this check exists for, as a broken derivation is for the semantic check above), and without a cap the part is exactly the key relation; for `knn` / `spatial`, every edge is among its source's `k` nearest (or within `radius_m`) candidates in the fitted space, or the reverse of one, every node has all of its own, and a `"distance"` weight equals the recomputed distance. `verification.json` records `graph: pass | fail | n/a`.

Required: `schema`, `recipe`, `manifest`, `manifest_digest` (the file's sha256), `verification` (with `structural` and `determinism`), `before_after`, `readings.abstract`. The apply script (`scripts/apply_shape_layer.py`) validates this, injects `assets/shape-render.js` + `assets/shape-layer.css` through the platform writer, adds a `<noscript>` fallback (the recipe table, before/after, the verification markers). Output path default `<input-stem>.shaped.html`; the input HTML is never modified; the shaped dataset files sit in `outputs.dir` next to it.

The render mounts one tab, `data-layer="shape"`, labelled **Shape**: a recipe table (step, op, columns, source chip linking to the geometry/analysis element it cites, rationale, consequences, alternatives folded), a before/after strip, a lineage graph (input columns → steps → output columns; dropped columns end at the step that dropped them, with the reason), the verification panel with its markers, and the forks with what was asked and answered. A `graph_edges` row of the recipe table shows its method and the counts (`n_nodes` per part, `n_edges`, `cross_part_edges`), and the manifest's `graph` block is rendered as one line beside the parts in the before/after strip (`method · level · directed · n_edges · edges file`) — absent when no such step ran. It reads only `layer-shape-data`, idempotent, empty state when missing, ≤ 60 KB, SVG only, keyboard-operable, `window.__shape = { steps(), lineage(), version }` for tests.

## 5. Naming, memory, hand-off

Output: `<input-stem>.shaped.html` next to the input (the chain's append rule: `orders.domain.analysis.html` → `orders.domain.analysis.shaped.html`); dataset files `<dataset-stem>.<part>.<ext>`, `recipe.json`, `manifest.json`, `lineage.json` and `reproduce_<slug>.py` in `shaped/` (or `--out-dir`); the working files in `.claude/dataset-shaper-runs/<UTC-timestamp>/`. Memory: `.claude/domain-forge-memory.md` § **Shaping stances** — one line per fork resolved (`YYYY-MM-DD | <dataset> | impute delivered_days: group-median by zip (indicator)`), read before compiling so a re-run does not re-ask; a `graph_edges` step's method is a Shaping stance in its own right (`YYYY-MM-DD | <dataset> | graph_edges: key_pair on customer_id (clique ≤ 20, symmetric)`), the one `/vega-forge` reads as the recorded stance behind its `graph` sample. Hand-off: the summary names the shaped files and the `manifest.json` as the input for training (and, when a `graph_edges` step ran, the `edges` part — `outputs.files.edges` — as what the graph families of `/vega-forge` read, inductive or transductive being that stage's decision), `/blueprint <out> --mode pipeline` for the pipeline architecture (the recipe phases are its ingestion/feature stages), and `/data-lens <out> --dataset shaped/<train file>` to re-analyse the shaped data if the user wants the drift module to compare before and after (`<out>` is the full output path).

**What proves the shaper serves every cell.** The backend coverage matrix (`vega-forge/scripts/tests/matrix/run_matrix.py --cells all`, report `vega/backend-matrix@1`) shapes its raw tables through this executor — the real `shape.py`, one shaped variant per question the cells ask: rows, windows on a time split, nodes with `key_pair` and `knn` edges and graphs with `key_pair` bonds within a `graph_id`, each with its `edges` part — before any network sees them, for every cell of `vega-forge/scripts/catalog.json`'s admission table (`vega-forge/references/family-catalog.md` §7). A shaper change ships only when that report is green (`summary.failed == []`) and its cell list equals the admission table (`admission.table: "equal"`); a sample shape the shaper claims and the matrix does not shape is a coverage defect, never a skip. The matrix proves sample shapes, not every op: the `spatial` edge method and the `lag` step are no admission cell, and they are proven by the shaper's own tests (`scripts/tests/test_graph_edges.py`, `test_transform_lag.py`) and the chain's lanes.
